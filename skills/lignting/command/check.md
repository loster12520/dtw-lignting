# lignting check —— Bug 排查（/lt-check、/ltck）

目标：用"信息收割 → codegraph 走查 → 有计划的插桩 → 假设排序"定位疑难 Bug 根因。
信条：**无法复现不等于没有线索，代码不会撒谎，只是我们没看到日志。**

## 输入

- **文字**：报错信息、复现步骤、操作路径、影响范围（哪个浏览器/角色/端）、发生时间。
- **附件可直接附**：报错截图、控制台日志、录屏、接口返回文件都行；**只有附件、没有文字也算
  有输入**，不要当成空输入——先读附件里的报错/堆栈，再按第 1 步补齐缺失信息（第 0 步照常先做）。
- **别名**：`/lt-check`、`/ltck` 等价。

## 空输入处理（先于第 0 步）

**触发条件**：只有命令本身，没有文字、也没有附件。

此时只输出一份小教程，然后停下：**不进入后续流程、不做流程级代码探索、不提问、不写文件、不建目录**，
也不问“要不要开始”。

- 教程按**当前项目真实文件/模块**重新组织，不复述种子案例里的示例名字。
- 动笔前最多花 3 步摸清项目：读 `README.md` / `package.json` / 最近 `git log -5` / 顶层目录结构。
  结构类查询用 codegraph，调用带 `projectPath`；**默认项目不是当前仓库时必须带**。
  本步不受第 0 步强制检查约束：没有索引就用上面这些轻量材料确认项目轮廓，不要卡在初始化。
- 教程必须覆盖：**用途 / 输入 / 流程 / 产物 / 当前项目实例 / 别名与下一层 / 3–5 条坑**。
  其中“当前项目实例”要落到真实文件/模块上，能让人照着找。
- 末尾给一句**可复制的下一步示例**（命令 + 一条具体报错/现象），不要用提问收尾。

## 小教程种子案例（只作结构种子）

- **场景**：点保存后列表不刷新，控制台报 `Cannot read properties of undefined (reading 'length')`。
- **用户可能怎么问**：`/ltck 点保存后列表没刷新，控制台这个报错，截图和日志在附件里`。
- **产出**：完整出现链路 + 复现方式 + 修复方案；推理中途先给假设排序和插桩计划。
- **结构种子**：用途 → 输入 → 流程（信息收割 → 探索成员走查 → 插桩 → 假设排序 → 终止）→
  产物 → 当前项目实例 → 别名与下一层 → 坑。
- **必须替换**：示例里的组件/函数/报错文案只是占位，教程里要换成当前项目真实文件与符号；
  不确定就继续用 README / `git log` / codegraph 确认，别照抄示例。

## 第 0 步：codegraph 前置检查

- 会话里有 `codegraph_status` 就调用它确认索引；**没有这个工具**就用 `codegraph_explore`
  带 `projectPath` 做等价检查（能返回当前项目的符号/文件即视为可用）。
- `projectPath` 指向当前工作目录；**默认项目不是当前仓库时必须带**，否则查的是别的仓库。
- 项目确实没有 `.codegraph/`（索引未初始化）→ 立即停止，要求用户运行 `codegraph init -i`
  后重试，不得用 grep/read 绕过探索。

## 第 1 步：信息收割（优先，不直接给结论）

先输出结构化 checklist，反问用户补齐（用户不知道就引导去查）：

1. **影响范围**：特定浏览器/版本？特定角色？云机端还是浏览器端？
2. **操作路径**：报错前具体点了哪几个按钮？（精确到操作顺序）
3. **环境快照**：控制台是否有红色报错？截图/文本都行。
4. **网络状态**：是否有接口返回非预期数据（null、undefined、超长文本、错误码）？

## 第 2 步：静态代码走查（必须下发探索成员）

- 按 SKILL.md §3 选路，**整轮只走一套，禁止混用**：
  - **Agent Teams 可用**（会话有 `wait_agent` 且 `team_task_create`）→ `spawn_teammate` 下发探索成员；
  - **Team 不可用** → 有 `subagent_explore` 就优先用它探索，否则回退 native `subagent`
    （**不传 `run_in_background`**，调用立即返回 child id）；
  - 两样都没有 → 主会话自己走查。`subagent_explore` 不是硬要求。
- 为每条可疑链路**下发探索成员**（Team 成员或子代理），追踪完整调用链、定位入口、
  理解上下文。涉及多条链路时一次并行下发多个，按链路切分任务。
- 结果用 `send_message` 回传或完成通知回到对话；等并发结果到齐再继续。
- 重点高危地带（前端通用）：
  - **异步时序**：setTimeout / Promise.all / 未 catch 的异常 / 组件卸载后残留的异步回调；
  - **状态残留**：卸载时是否清理监听器/定时器/subscription；
  - **数据边界**：可选链缺失、数组越界、接口 null/undefined 导致渲染崩溃。
- 若项目内有踩坑记录（如 `<项目根>/.dsh/skills/` 或 `<项目根>/.agents/skills/` 下的
  check/pitfalls 类文件），先读取；排查中发现新的通用模式则追加回该记录。

## 第 3 步：插桩策略（多轮推进，先计划后动手）

- **第一轮优先要信息**（第 1 步）；信息不足时不急着插桩。
- 仍无法 100% 确定根因时，**先输出一份插桩计划**给用户确认，再动手。插桩计划必须包含：
  1. 预估 bug 出现的整体调用链路（哪里进、哪里出、哪段最可疑）；
  2. 在哪些位置插桩（文件 + 函数 + 具体变量）；
  3. 每处插桩能获取到什么信息；
  4. 插桩出现异常（日志缺失/值不对/时序错）分别能说明什么。
- 日志统一用 `[DEBUG-lignting]` 前缀，方便用户在控制台筛选。
- **用户确认计划后才插桩**；插桩产物是临时诊断代码，定位后必须清理。
- **若用户说明目前无法复现**：不再推销插桩计划，改为每轮更深入地从代码侧推断
  （调用链、时序、状态机、双端差异），并引导用户说出你认为不确定的隐形条件
  （环境、账号、数据规模、并发、埋点配置等）；单轮最多 3 个假设，
  超 3 轮仍无进展则明确请用户提供录屏/更细操作时间线。

## 第 4 步：假设排序与验证

给出 ≤3 个假设，按可能性百分比排序，每个必须附带验证方法（打印什么、看什么、能排除什么）。

## 第 5 步：终止与输出

- 假设命中 → 直接输出：**完整出现链路 + 复现方式 + 修复方案**（含修复代码），
  修复需用户确认后再改。
- 全部落空 → 回到第 1/3 步循环或请用户补充材料，绝不无限猜测。
- 排查完成：若发现新的通用踩坑模式，写回项目的踩坑记录。
