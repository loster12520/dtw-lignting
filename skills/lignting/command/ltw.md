# lignting Wands —— 权杖层 · 具体执行（/ltw）

目标：吃下一轮的详细计划，**动手写完代码、跑完自测**，产出四段式执行汇报。

> **偏离必须明说。**
> 计划是几小时前的快照，代码是现在的现实，两者对不上是常态。
> 可以偏离（现场信息永远比计划多），但**不许默默绕开**——默默绕开等于让计划文档变成谎言，
> 而下一轮还要拿它当输入。

## 输入

- 上游详细计划（通常 `.lignting/<feature>/phase-<n>/round-<m>.md`）
- 上一轮执行报告（`phase-<n>/round-<上一轮>.report.md`，若有）——里面有影响本轮的信息
- **可以随命令附图片 / 文件**：计划文档、报错截图、日志、设计稿都能直接附在命令后面
  （例如 `/ltw 按这份计划做完 <附计划>`）。附件内容算输入的一部分，不要让用户再复述。
- **只有附件、没有文字也算输入**：从附件里定位计划与范围，按第 1 步开始；**不得当空输入处理**。
- **空输入**：只有命令本身，既没有文字也没有附件，才算空输入——按下面「空输入处理」先出小教程。
- **`roadmap.md` 不是输入**：它是人读总计划视图（格式见
  [roadmap-format.md](../references/roadmap-format.md)），冲突以本轮计划文档为准。
- **别名**：`/ltw` = `/lt-wands`，行为完全一致；其他写法以 `SKILL.md` 路由表为准。

读计划时**同时读它的「与上游的偏离」节**——了解这份计划本身是怎么变过来的。

## 空输入处理（先于第 1 步）

**判定**：空输入 = 只发了 `/ltw`，**既没有文字、也没有附件**。给了文字或附件就是有效输入，
走正常流程。

空输入时**不进入正式流程**（本文件从第 1 步开始）：不读代码、不提问、不改任何文件、
不动 whatsnext——直接在对话里输出一篇**本命令的小教程**。

教程不是写死的模板，**由模型按当前项目现场重新组织**，例子必须是这个项目里真实存在的文件/模块。

**先确认项目（最多 3 步，做完就写）**：

1. 读 `README` / `package.json`（或其他语言的等价清单），确认项目是什么、怎么构建与检查。
2. 看最近几次 `git log --oneline -10`，了解当前在做什么。
3. 需要结构信息时用 codegraph 查（`codegraph_explore`，带 `projectPath`），或列一下顶层目录。

**教程结构（顺序固定，内容按项目填）**：

1. **用途与适用** —— 吃一轮详细计划、写代码并给出四段式汇报；没有可执行计划先 `/ltp`，
   方向未定回 `/lts`。
2. **输入怎么给** —— 需要已确认的分轮计划（含「与上游的偏离」节），怎么随命令附图片/文件，
   什么算空输入。
3. **分步流程与判断标准** —— 执行前确认（计划已确认、范围已看、上轮报告已读）→ 按顺序执行、
   当步验证 → 偏离处理（跳过/补做/换路线，**一律记偏离**）→ 自测逐条 → 四段式汇报 →
   落盘 `report.md` → whatsnext 同步 + 回填 roadmap → 收尾；判据是"真命令、真输出，不粉饰"。
4. **产物与落盘路径** —— 代码改动 + 对话里的四段式汇报 + 落盘
   `phase-<n>/round-<m>.report.md`；勾 whatsnext 的 `plan.md`；回填 roadmap §4/§1/§6；
   **不直接改 `index.md` frontmatter**。
5. **当前项目实例** —— 用刚确认的真实文件/模块与真实检查命令，举一个"这轮会改什么、怎么验"的例子。
6. **别名与下一层** —— 列出别名；写清收尾推荐：正常完成接 `/ltp … 细化下一轮`，
   影响后续先 `/lts` 或修 `phases.md`，阶段完成接 `/ltp … Phase 2`。
7. **常见坑（3–5 条）** —— 本层最容易犯的错（默默偏离、顺手改范围外代码、
   用"应该没问题"代替验证输出等），每条给一句避法。

教程直接在对话里输出。**不写文件、不建目录、不问"要不要开始"**——末尾给一句可直接执行的示例命令即可。

## 小教程种子案例（只作结构种子）

> 以下是**结构种子**，只示范教程该长成什么样；**输出教程时必须替换为当前项目的真实文件/模块，不得照抄**。

- **场景**：`round-1.md` 计划"先加一层适配垫片、再删旧调用"，需要按顺序执行并给出四段式汇报。
- **用户可能怎么问**：`/ltw .lignting/config-layer/phase-1/round-1.md`（或只发 `/ltw` 的空输入）。
- **产出**：按计划顺序改代码、每步跑真实验证并记录输出；四段式汇报（做了什么/验证结果/
  与计划的偏离/影响后续轮次的问题）并落盘 `report.md`；勾 whatsnext、回填 roadmap 并给下一步命令。
- **教程里必须替换**："适配垫片"要换成当前项目真实的文件/符号，验证命令要用该项目
  真实存在的检查命令，偏离示例也要贴合本项目的代码现实。

## 第 1 步：执行前确认

- 计划已确认过（未经确认的计划不执行）。
- 计划的「本轮范围」和「明确不做」看清楚了。
- 上一轮的执行报告 `report.md`（若有）已读——里面有影响本轮的信息。

## 第 2 步：按顺序执行

- **严格按计划的改动顺序走**。顺序本身是设计的一部分（为了中间态不坏），
  不要图省事打乱。
- 每步做完**当步验证**，不攒到最后。
- 验证按计划里给的命令跑，**记录真实输出**（不是"应该没问题"）。

## 第 3 步：遇到偏离怎么办

| 情况 | 做法 |
|---|---|
| 计划里某个改动实际不需要 | 跳过，记进偏离 |
| 计划漏了一个必要改动 | 补做，记进偏离 |
| 计划的技术路线走不通 | 换路线，记进偏离；**若影响后续轮次，立即停下问用户** |
| 途中发现无关的坏味道 | **不要顺手改**，记进"影响后续轮次的问题" |

范围纪律：**只做本轮范围内的改动**。发现别的问题记下来，不在本轮动手。

## 第 4 步：自测

按计划的「验收标准细化」逐条跑，一条不漏：

- 跑真命令，记真输出。
- 失败的条目标明失败，**不粉饰、不"应该没问题"**。
- 有跳过没跑的条目 → **单独列出来**，说明为什么跳过。

## 第 5 步：四段式汇报（本层的核心产物）

### 1. 做了什么

改动的文件清单 + 每处改了什么（简明，不贴大段代码）。

### 2. 验证结果

| 验收条目 | 命令 | 结果 |
|---|---|---|
| 1 | `npm run check` | 通过 / 失败（附输出） |

**必须贴真实命令与真实输出**。"已完成""正常"不算验证结果。

### 3. 与计划的偏离

| # | 计划 | 实际 | 理由 |
|---|---|---|---|
| 1 | 改 A 方法 | 改为新增 B 方法 | A 被 C 强依赖，改动会连带 |

**这一节不许为空。** 真的零偏离时，写一行"无偏离"并说明为什么计划这么准
（比如"计划基于完整依赖闭包分析，实际与预期一致"）——**但要诚实**，
没有计划能精准到零偏离，空着或含糊带过都说明没认真核对。

### 4. 影响后续轮次的问题

执行中发现、但不属于本轮范围的东西：隐藏耦合、技术债、计划里的错误假设。
**这一节是整条链的回灌通道**——它是唯一能把"计划错了"传回去的管道，
发现什么就写什么，不要判断"这个重不重要"。

### 落盘：round-<m>.report.md

四段式汇报在对话里输出后，**同文落盘**到
`.lignting/<feature>/phase-<n>/round-<m>.report.md`：

```markdown
# 执行报告 · <feature> · Phase <n> · R<m>

> 层级：权杖
> 核心目的：<从本轮计划抄一句；计划没写就写“计划未标核心目的”并提醒用户补>
> 日期：<yyyy-mm-dd>

## 1. 做了什么
## 2. 验证结果
## 3. 与计划的偏离
## 4. 影响后续轮次的问题
```

- report 的正文就是对话里那四段，**不改写、不另加第五段**；核心目的必须与本轮计划一致。
- report 是执行产物，**不是任何命令的输入**；下一轮只读计划，回看历史才读 report。
- 落盘后告诉用户文件路径；它会进 roadmap §4 与 §6（见第 6 步）。

## 第 6 步：同步 whatsnext 与回填 roadmap

按 [whatsnext-bridge.md](../references/whatsnext-bridge.md) 第四节执行：

1. 勾掉 whatsnext 任务 `plan.md` 里对应的 `- [ ]` → `- [x]`（可附结果摘要）。
2. 给出"当前进度"文本，供用户下次 `/wn-save` 使用。
3. 发现**已验证、可复用、自包含**的经验 → 提醒用户 `/wn-promote`。
   **失败尝试与未决研究不要提升。**

小阿卡那各层**不直接改 `index.md` 的 frontmatter**（`progress` / `updated` 走 `/wn-save`）。

### 回填 roadmap

执行与自测完成后，按 [roadmap-format.md](../references/roadmap-format.md) 回填
`.lignting/<feature>/roadmap.md`（先读最新全文、按 heading 用 edit 精确改；
**只回填实际发生的事实，不写计划、不写状态**）：

1. **§4 执行回填**：追加一行——轮次 | 做了什么 | 验证结果（真命令 + 真结果）| 与计划的偏离 |
   链接（[report](phase-<n>/round-<m>.report.md) · [计划](phase-<n>/round-<m>.md)）；
   影响后续轮次的问题在行末追加「→ 影响后续：…」。只追加、不改历史，写错用新行「更正 R<m>：…」。
2. **§1 现状行**：改成最近回填点（带日期），指向本轮 §4 行。
3. **§6 文档地图**：把 `phase-<n>/round-<m>.report.md` 行补成真实链接（round 文档行若已有则不动）。
4. **不动 §2/§3/§5**；不写完成状态；头部「最后同步」改当天；roadmap 不存在时先按格式建
   最小框架再回填；发现 roadmap 与源文档不一致 → 对话里说明并在计划文档「与上游的偏离」记录，
   不静默改。

## 第 7 步：收尾

给命令前先确认：四段式汇报已落盘 `report.md`、roadmap §4/§1/§6 已回填（第 6 步）。

给一句可粘贴的下一步命令：

| 情况 | 推荐 |
|---|---|
| 本轮正常完成，还有下一轮 | `/ltp .lignting/<feature>/phases.md Phase 1`（细化下一轮） |
| 发现的问题影响后续轮次 | 先 `/lts` 重想方向，或同步修订 `phases.md` |
| 整个阶段完成 | `/ltp ... Phase 2` |

## 不要做的事

- 不要默默偏离计划。
- 不要顺手改本轮范围外的代码。
- 不要用"应该没问题""已完成"代替真实验证输出。
- 不要丢掉失败的验证条目。
- 不要把失败尝试当经验提升到 whatsnext。
- 不要把四段式汇报只留在对话里、忘记落盘 `round-<m>.report.md`。
- 不要漏回填 roadmap §4/§1/§6，也不要把 roadmap 当状态台账写"已完成"。
- 不要把 report 当命令输入传给下一轮——下一轮只读计划。
