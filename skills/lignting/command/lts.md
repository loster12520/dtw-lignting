# lignting Swords —— 宝剑层 · 想法讨论（/lts）

目标：用户给一个**还没成形的想法**，agent **陪着把它想清楚**，最后沉淀成一份自包含的
**方向文档**，供下一层（`/ltc`）排阶段。

> **这层只谈方向，不谈实现。**
> 目标是"往哪走、为什么这么走、代价是什么"，不是"改哪个文件、加哪个函数"。
> 一旦开始谈具体落点，就说明该往下一层走了。

## 适用与不适用

| 适用 | 不适用 |
|---|---|
| 想法还在成形，需要探讨 | 需求已经清楚，只需排期 → 直接 `/ltc` |
| 涉及多处改动 / 数据模型 / 不可逆决策 | 单点小改动 → `/ltpl` |
| 用户自己的方案想被压测、想找盲点 | 已知怎么做，只要计划 → `/ltp` |

用户明显不需要讨论时，直说并推荐正确的层，不要为了走流程而强行讨论。

## 输入

- **要什么**：一个还没成形的想法、一处想不清楚的方向，或一个想被压测的既有方案。
  不需要成文文档，也不需要准确落点。
- **可以随命令附图片 / 文件**：截图、草图、报错日志、旧方案、竞品截图等都能直接附在命令后面
  （例如 `/lts 这个界面怎么整理 <附截图>`）。按附件内容理解意图，不要让用户再把附件复述一遍。
- **只有附件、没有文字也算输入**：从图里的问题、日志里的现象直接进入正常讨论流程
  （从第 0 步接续开始），**不得当空输入处理**。
- **空输入**：只有命令本身，既没有文字也没有附件，才算空输入——按下一节先出小教程。
- **`roadmap.md` 是本命令的输出、不是输入**：它是人读总计划视图（格式见
  [roadmap-format.md](../references/roadmap-format.md)）；讨论以 `direction.md` 与
  `direction.dialogue.md` 为准。
- **别名**：`/lts` = `/lt-swords`；`/lt-discussion`、`/ltds` 也路由到本层（以 `SKILL.md`
  路由表为准）。用别名、或只说"想先聊聊这个想法"，都按本文件处理。

## 空输入处理（先于第 0 步）

**判定**：空输入 = 只发了 `/lts`，**既没有文字、也没有附件**。给了文字或附件就是有效输入，
走正常讨论流程。

空输入时**不进入正式讨论流程**：不判断讨论重点、不做流程级代码探索、不提问、不建 whatsnext 任务、
不改任何文件——直接在对话里输出一篇**本命令的小教程**。

教程不是写死的模板，**由模型按当前项目现场重新组织**，例子必须是这个项目里真实存在的文件/模块。

**先确认项目（最多 3 步，做完就写）**：

1. 读 `README` / `package.json`（或其他语言的等价清单），确认项目是什么、入口在哪、怎么跑。
2. 看最近几次 `git log --oneline -10`，了解当前在做什么。
3. 需要结构信息时用 codegraph 查（`codegraph_explore`，带 `projectPath`），或列一下顶层目录。

**教程结构（顺序固定，内容按项目填）**：

1. **用途与适用** —— 本层解决什么问题、什么情况该用、什么时候该跳层（引「适用与不适用」）。
2. **输入怎么给** —— 要什么样的想法/材料，怎么随命令附图片或文件，什么算空输入。
3. **分步流程与判断标准** —— 从第 0 步到收尾，每步一句"做什么 + 怎么算做对"，
   重点点出"该拓宽还是该收窄、何时定型"的判据，以及每轮"先判断 → 3–4 个四段式问题
   → 对话记录"的节奏（内部相名不对外说）。
4. **产物与落盘路径** —— 方向文档包含哪些章节、默认落在 `.lignting/<feature>/direction.md`；
   落盘后创建/更新 `roadmap.md` 框架。
5. **当前项目实例** —— 用刚确认的真实文件/模块举 1–2 个例子：在**这个项目**里 `/lts` 大概会讨论什么。
6. **别名与下一层** —— 列出别名；写明产出方向文档后接 `/ltc <path>`。
7. **常见坑（3–5 条）** —— 本层最容易犯的错（过早收窄、在开放问题上给选项、用总结收尾等），
   每条给一句避法。

教程直接在对话里输出。**不写文件、不建目录、不问"要不要开始"**——末尾给一句可直接执行的示例命令即可。

## 小教程种子案例（只作结构种子）

> 以下是**结构种子**，只示范教程该长成什么样；**输出教程时必须替换为当前项目的真实文件/模块，不得照抄**。

- **场景**：项目已有可运行的命令行入口，用户想加"导出当前状态"的能力，但不确定该做成子命令、配置项还是独立脚本。
- **用户可能怎么问**：`/lts 我想加个导出功能，但没想好做成什么形态`（也适用只发 `/lts` 的空输入）。
- **产出**：先拓宽出两三个候选形态（含"先不做"），逐个压测代价后收窄，最后落一份方向文档
  （目标/非目标、关键决策、待决问题），并建 `roadmap.md` 框架，收尾推荐
  `/ltc .lignting/<feature>/direction.md`。
- **教程里必须替换**：把"命令行入口"换成当前项目真实的入口文件/模块与命令名，
  把"导出"换成该项目里能对应上的真实能力。

## 局部例外（覆盖公共约束）

- **`codegraph` 门槛放宽**：本层**不做** `codegraph_status` 强制前置、不因项目无
  `.codegraph/` 而停止。架构讨论常常发生在代码之前，强制索引会把场景卡死。
  需要结构信息时，能用 codegraph 就用；不可用时改用读关键文件或直接问用户。
- **下发方式按 `SKILL.md` §3 选路，不写死探索工具**：Agent Teams 可用时优先用 Agent Teams
  分工（队长统筹、成员分头探索与判断）；不可用时按 §3 回退——会话有 `subagent_explore`
  就用它探索，否则用 native `subagent`。`subagent_explore` **不是硬要求**，不因缺它而停止本层。
- **探索成员允许下判断**：本层的探索成员不只回符号清单，可以回"现状约束 + 可疑点"，
  但每条必须标依据强度（`[事实·依据]` / `[推断·依据]` / `[猜想·待验证]`）并写清验证路径；
  结论由本层汇总判断，不要让成员替你拍板。
- **提问规范（`SKILL.md` §4.2 在本层的落法）**：每轮 **3–4 问、硬上限 4**，不足 3 个不凑数，
  四段式缺一不可；开放问题禁止给选项、推荐答案写成倾向，分叉决策才用 `ask_user_question`
  且推荐项第一；对外不播报层/相标签。见 2.2 与第 3 步。

## 第 0 步：接续（跨对话能力的关键）

按 [whatsnext-bridge.md](../references/whatsnext-bridge.md) 第四节执行：

1. 检查 `<项目>/.whatsnext/tasks/` 有无在进行任务。
2. 有则读 `index.md` → 按其中的**文件索引**懒加载 `.lignting/` 下的历史文档。
3. **把已讨论、已否决的内容带入本轮，不重复提问。**

同时读 `direction.dialogue.md`（若存在），接上未聊完的开放问题。

找不到任务不阻塞，直接开始讨论。

## 第 1 步：判断当前讨论的重点（内部）

讨论的重点有四种典型节奏，判据见下。**这四个相名只是你的内部判断标签，不要写进回复**，
也不要对用户宣布"现在在什么相/什么层"；重点变化时的自然过渡写法见 2.1。

| 相 | 在干什么 | 禁止 |
|---|---|---|
| **发散** | 拓宽可能性，多出两三个候选形态（**包括"什么都不做"**） | 禁止评价、禁止比较优劣、禁止收敛 |
| **压测** | 用对抗性问题打候选方案 | 禁止提新方案，只打现有的 |
| **收敛** | 缩小到一两个方向，**开价** | 禁止引入新选项 |
| **定型** | 方向已定，落成文档 | 禁止再翻案（除非用户提出） |

判定规则：

- 想法模糊 / 用户在用"我想""大概""类似"→ **发散相**
- 已有明确方案，用户想听意见 → **压测相**
- 候选收拢到两三个 → **收敛相**
- 用户说"就这样""开始写吧" → **定型相**

判断结果只影响你怎么推进（该拓宽、该压测、该收窄还是该定型），不对外播报。

**不允许跳步**。从发散直接跳到"二选一"是最常见的错误——那等于把用户的思考框在
你的选项里。宁可多聊一轮。

## 第 2 步：重点过渡（2.1）与四段式问题（2.2 / 2.3）

2.1 只在**讨论重点变化**时写；2.2 是每个问题的标准结构，2.3 是其中的回指链接细则。
这些规定属于公共约束 §4.2；本层只在该基础上补充更严的细节（开放问题不给选项、
推荐答案必填）。

### 2.1 重点切换时的自然过渡（只在重点变化的那一轮写）

**检测**：本轮要回答的重点 ≠ 上一轮对话记录里的重点 → 写一段过渡；重点没变（比如用户只是
补了句事实、回答了你上一个问题）→ **不写**，直接给判断与问题。不要为了仪式感每轮复述。
第一次开口、或对话记录还没写 → 不写过渡，自然开场即可。

**写法**：先用一两句自然的话把上下文递过去（比如"上面把方向收窄到两个，接下来该看代价了"），
再给下面这段"状态交接"：

```markdown
已确定的：
1. <一句话结论> —— [依据或回指]
2. <一句话结论> —— [依据或回指]

到这里还没定的：<一句话；没有就写"无">
本轮要做的：<要回答什么；一句话写清"换的是什么重点">
```

| 骨架位 | 要求 |
|---|---|
| 已确定的 | 只写**当前真的站得住的**，每条附依据或回指链接；没有就给一句"目前还没有站得住的结论"——**不许编** |
| 到这里还没定的 | 一句话，防止用户以为全都定了 |
| 本轮要做的 | 写"变的是什么"，不写"再聊聊" |

**不写标签**：不要写"相变：X → Y""当前相：Y""进入下一相""退回 X 相"，也不要在任何对外
文字里出现层名/相名（`宝剑层`、`发散相` 等只属于文档元数据与内部判断）。用户推翻上一轮结论时，
同样用自然过渡写清"哪条作废、改向去哪"，不要用"退回 X 相"。

**确定性**：每条结论后用回指链接（见 2.3）指回它是哪一轮定下来的；
尚不确定的就地标 `[猜想·待验证]`，**不许混进"已确定"里**。

过渡写在回复开头，**写完再给判断与问题**，不要塞进文末或折叠块。

**写完必须落盘**：本轮结束追加对话记录时，把这组结论写进当前轮的 `## L<n>` 正文
（"本轮确定的结论"小节），下一层的回指才能指得到。对话记录里**不要写"相变/当前相"字样**，
需要说明时写"这一轮把重点从 A 转到了 B"。

> 本层的重点默认是"一个重点聊几轮"，**不是每轮都切**：不切的轮次不写过渡，只正常给
> 判断与问题。别把过渡变成每轮都念一遍的仪式。

### 2.2 四段式问题（背景 / 问题 / 为什么这么考虑 / 推荐答案）

用户手里没有你的上下文。**每个问题都要让用户从零读懂，并看到你的倾向**——
没有推荐答案的问题不许问。

**四段（顺序固定，缺一不可）**：

1. **背景** —— 1～3 句：这事从哪来的、前文聊到哪一步、现在卡在哪；引用已定结论或
   被否决方案时带回指链接（见 2.3）。
2. **问题** —— 一行一个问句，一问只做一个决策。
3. **你为什么这么考虑** —— 你的判断、推理链与依据、不确定点、不同回答会改变什么；
   另一种可能是 Y 时，把它的代价 Z 一起说清。
4. **推荐答案** —— 明确推荐一个答案 + 理由 + 选错的代价。

**两种问法的落点**：

| 类型 | 怎么问 | 选项 | 推荐答案 |
|---|---|---|---|
| 开放问题（还在长，不是互斥选择） | 普通对话直接问 | **不给选项** | 写成"我倾向 X，因为…"，不写成 A/B/C |
| 分叉决策（两边都通 + 只能选一 + 选错返工） | `ask_user_question` | 给选项，**推荐项放第一位**；`header` 只放短标签（≤6 字） | 四段全部写进 `question` 字段，段间用换行 |

**每轮问几个**：**3–4 个最核心的问题，硬上限 4**。

- 真正阻塞的不足 3 个 → **不凑数**，可以只问 1–2 个；
- 超过 4 个 → 只问最核心的 4 个，其余列成"待问清单"（只列问题标题）放进本轮对话记录，
  下一轮再问；
- 优先问"不问就定不下来"的，不问"顺便确认"的。

**不许用没解释过的内部黑话提问**：对话记录里的代号、简称、层名、文件名第一次出现在
问题里时要带一句解释或链接。

### 2.3 回指链接（四段式第 1、3 段里必须带）

引用**之前任何一轮讨论过**的术语、结论、被否决方案时，**必须**带上可点击的回指链接，
不带就是"不知所云"的直接来源。

```markdown
<术语>（[见 L3 · whatsnext 能不能配合](direction.dialogue.md#l3--whatsnext-能不能配合)）
```

- 链接格式：`[文字](<对话记录路径>#<该轮标题的小写锚点>)`；相对当前文件写路径——
  同在 `.lignting/<feature>/` 下就写 `direction.dialogue.md#…`。
- 锚点取那轮的标题 `## L<n> · <主题>`：**全小写 → 删掉所有标点（含 `·`）→ 空格换 `-`**；
  标题里的英文与数字原样保留。
- 方案文档在对话里被引用时同理：`[direction.md 第 2 节](direction.md#2-关键决策记录)`。
- 术语第一次出现才需要带链接，同一条回复里第二次出现可以省。
- **点开链接落不到具体小节时，文字部分要能独立看懂**：链接文字里带上
  `L3 · whatsnext 能不能配合` 这种"文件内位置"，即使锚点没生效也知道去哪找。

## 第 3 步：开放问题 vs 分叉决策（本层的核心技巧）

必须区分**开放问题**和**分叉决策**。把它们混为一谈，讨论就死了。两者的统一结构见 2.2。

### 开放问题——还在长的事

用**普通对话**直接问，**不给选项**；但推荐答案必须有（你的倾向 + 理由 + 选错代价）。

回应顺序（对应四段式，不能反）：

1. **背景**：这事从哪来、前文到哪、现在卡在哪；
2. **问题**：你最想先弄清的那一个问句；
3. **你为什么这么考虑**：你倾向什么、依据是什么、担心哪里、另一种可能是 Y 及代价 Z；
4. **推荐答案**：你推荐哪边、为什么，并说清代价。

禁止在开放问题上用 `ask_user_question` 给一组选项让用户挑。

### 分叉决策——真的互斥了

到这一步才用 `ask_user_question`：带选项、**推荐项放第一位**，四段式（背景/问题/为什么这么
考虑/推荐答案）全部写进 `question` 字段，段间用换行；`header` 只放短标签（≤6 字）。
每轮 3–4 问、硬上限 4，与 2.2 同一规则。

**判定标准**：两边都说得通、且只能选一个、且选错要返工——才是分叉。
只是"还没想清楚"不算分叉，别急着让它变成选择题。

## 第 4 步：每轮必做的四件事

1. **先给判断与证据**：先回答"你怎么看"——判断 + 依据（文件/符号/命令输出/回指）+
   不确定点（标 `[猜想·待验证]` 并给验证路径），再提问。不要一上来就抛问题。
2. **再问 3–4 个最核心的问题**：按 2.2 四段式写；硬上限 4，真正阻塞不足 3 个不凑数，
   超出列"待问清单"下一轮再问。
3. **抛一个反直觉视角或反例**——每轮至少一个。这是讨论有没有价值的试金石；
   通篇顺着用户说，等于没参与。
4. **追加对话记录**（按 [dialogue-log-format.md](../references/dialogue-log-format.md)）。
   每轮结束就写，不要攒；**重点变化那轮**要把"已确定的结论"落到该轮正文，
   **不写相名/层名标签**。

### 标注确定度（全程强制）

| 标记 | 含义 | 要求 |
|---|---|---|
| `[事实·依据]` | 已验证 | 附依据（文件/符号/命令输出） |
| `[推断·依据]` | 从事实推出来的 | 附依据 + 推理链条 |
| `[猜想·待验证]` | 没验证的直觉 | **必须给验证路径** |

**纪律不是"不许说没验证的"，而是"说清哪句没验证"。**
为了保住"必须已验证"而不敢提猜想，会让讨论失去全部价值。

### 架构视角自查清单

给意见时对着这张表过一遍，挑相关的说——**不要每次都全念一遍**：

- **变化成本**：加一个新维度要改几处？改一处=边界画对了；改 N 处=该重画边界。
- **不变量与隐性耦合**：哪些东西被默认"永远如此"？那正是三个月后炸的地方。
- **可逆性**：这是单向门还是双向门？**单向门现在必须较真，双向门应该故意推迟。**
- **代价与风险分列**：**代价是必然付的，风险是可能付的**，不要混成一张表。
- **运维 / 认知成本**：多一层抽象、多一个进程、多一份要同步的状态——谁付账、什么时候付。
- **是否过早抽象**：是不是在为还不存在的第二个用例设计。

## 第 5 步：讨论成形 → 推荐开跨对话任务

**时机**：方向大致成形、准备沉淀文档时——不是一进门就建。

推荐给用户一句可直接粘贴的命令：

```
/wn 开始小阿卡那任务：<任务名>
```

任务名用短横线小写，与 `.lignting/<feature>/` 的 feature 名保持一致。
**不代跑这一步**，交由 whatsnext 自己的流程（理由见
[whatsnext-bridge.md](../references/whatsnext-bridge.md) 第二节规则 2）。

`.whatsnext/` 未初始化时，先推荐 `/wn-init`。

## 第 6 步：输出方向文档

讨论收口时输出**方向文档**，章节清单如下（顺序可调，内容不可省）：

1. **目标与非目标** —— 目标一句话说清；**非目标 = 明确不做的事**（这条最常被省，也最该写）。
2. **关键决策记录** —— 每条：结论 / 为什么 / **被否决的方案及其理由**。
   被否决的部分是这份文档最值钱的内容。
3. **架构方向** —— 分模块或多端的形态、职责归属、数据流向。
   允许抽象，但要说清边界画在哪、为什么画在那。
4. **不可逆的架构契约** —— 数据模型、协议、边界归属这类改起来会连锁破坏的东西。
   **这些要写死**；"用哪个类实现"之类留给下一层。
5. **待决问题** —— 现在不该决定的事。写明"为什么现在不定"和"到哪一层必须定"。
   **允许以待决问题收尾**——硬决定比不决定更糟。
6. **风险与代价** —— 分两列（代价必然付，风险可能付）。
7. **验证信号** —— 将来怎么知道这个方向是对的？给可观察的信号，不是"感觉良好"。
8. **阶段初步勾勒** —— 只列阶段名与大致边界，**不要展开**。展开是 `/ltc` 的活。

写法遵守 [plan-doc-format.md](../references/plan-doc-format.md)：带头部（上游/对话记录/
日期）、关键结论带回指、末尾有「与上游的偏离」节（本层为起点则写"无上游"）。

### 落盘

1. 先在对话里输出全文让用户过目。
2. 问保存路径，**默认建议** `.lignting/<feature>/direction.md`。
3. direction.md 落盘后，按 [roadmap-format.md](../references/roadmap-format.md) 建/更新**总计划框架**
   `.lignting/<feature>/roadmap.md`（不存在则新建；已存在则只改头部 / §1 / §5 方向组 /
   §6 前两行。先读最新全文，按 heading 定位、用 edit 精确写，不整文件重写）：
   - 只写：头部（类型/基准/最后同步）、§1 一句话现状与目标（现状指针 / 目标 / 待拍板三行）、
     §5 决策索引的**方向组**（每条 `- 方向：<一句话> —— [L<n> · 主题](direction.dialogue.md#锚点)`）、
     §6 文档地图的**表头 + 前两行**（`direction.md`、`direction.dialogue.md`）；
   - §2/§3/§4 只留节标题 + 纯文字「待 /ltc（或 /ltp、/ltw）填充」，**不预写阶段/轮次**；
   - §1 的「待拍板」链 `direction.md` 第 5 节，阶段归属写成"待 /ltc 生成"（不写死链）；
   - roadmap 是**人读总计划视图，不是命令输入**；细节标注「派生自 <源文档> · 同步于 <日期>；
     冲突以源文档为准」；**不写完成状态**；**不登记** whatsnext 的「文件」索引；
   - 四层方案文档继续按 plan-doc-format 写 `> 层级：` 头部，roadmap 用「类型 / 基准 / 最后同步」。
4. 落盘后把 direction.md 路径写进 whatsnext 任务 `index.md` 的「文件」索引（纯 Markdown 编辑）。
   任务尚未创建时，跳过并在收尾提醒。
5. **不要写状态字段**——进度只认 whatsnext；roadmap 也不写状态。

## 第 7 步：收尾

1. 告知本文档是**方向级**结论，不是可开工粒度。
2. 给**一句可粘贴的下一步命令**：

   ```
   /ltc .lignting/<feature>/direction.md
   ```

## 不要做的事

- 不要在文档里写具体文件路径、函数名、字段表（除"不可逆架构契约"外）。
- 不要做阶段排期和验收标准——那是 `/ltc`。
- 不要在开放问题上给选项；分叉决策才用 `ask_user_question`，且推荐项放第一位。
- 不要问**没有推荐答案**的问题——每个问题都要给倾向、理由和选错代价——见 2.2。
- 不要一轮问超过 **4** 个问题；真正阻塞的不足 3 个时不要凑数——见 2.2 / 第 3 步。
- 不要顺着用户说；每轮至少一个反直觉视角。
- 不要用"总结：1. 2. 3."收尾——那是文档口吻，讨论该以判断和问题收尾。
- **不要播报层名/相名**：不要写"当前层""当前相""相变：X→Y""退回 X 相"——重点变化时
  用自然过渡（已定 / 未定 / 本轮要做什么）——见 2.1。
- 不要提**没有背景**的问题：任何问题（含 `ask_user_question` 的 `question`）都要先交代
  它从哪来、前提是什么，四段缺一不可——见 2.2。
- 不要**裸引用**前文的术语或代号：第一次出现必须带回指链接——见 2.3。
- 不要漏了落盘后的 roadmap 框架（§1 / §5 方向组 / §6 前两行），也不要提前写 §2/§3/§4。
