# lignting plan —— 需求规划（/lt-plan、/ltpl）

目标：把一条需求描述变成一份可直接开工的完整修改计划，中间只问该问的问题，
不反复确认已经明确的方向。

## 输入

- **必需**：需求描述（一句话到一段都行）。越具体越好：改哪个页面/接口、参照什么样式、
  字段名、端侧（云机 / 浏览器）。
- **附件也算输入**：随命令附的截图、设计稿、需求文档、报错日志可直接用；
  **只有附件、没有文字也算有输入**，不要当成空输入。
- **别名**：`/lt-plan`、`/ltpl` 等价；注意它和 `/ltp`（星币层）只差一个字母，`/ltpl` 是轻量规划。

## 空输入处理（先于第 0 步）

**触发条件**：只有命令本身，没有文字、也没有附件。

此时只输出一份小教程，然后停下：**不进入后续流程、不做流程级代码探索、不提问、不写文件、不建目录**，
也不问“要不要开始”。

- 教程按**当前项目真实文件/模块**重新组织，不复述种子案例里的示例名字。
- 动笔前最多花 3 步摸清项目：读 `README.md` / `package.json` / 最近 `git log -5` / 顶层目录结构。
  结构类查询用 codegraph，调用带 `projectPath`；**默认项目不是当前仓库时必须带**。
  本步不受第 0 步强制检查约束：没有索引就用上面这些轻量材料确认项目轮廓，不要卡在初始化。
- 教程必须覆盖：**用途 / 输入 / 流程 / 产物 / 当前项目实例 / 别名与下一层 / 3–5 条坑**。
  其中“当前项目实例”要落到真实文件/命令上，能让人照着敲或照着找。
- 末尾给一句**可复制的下一步示例**（命令 + 一条具体需求），不要用提问收尾。

## 小教程种子案例（只作结构种子）

- **场景**：单点小改动——给登录页加“忘记密码”入口。
- **用户可能怎么问**：`/ltpl 登录页加一个忘记密码入口，点进去是 /forgot-password`。
- **产出**：一页可直接开工的修改计划（需求描述 + 按文件分组的改动 + 边界/失败场景 + 明确不做的事）。
- **结构种子**：用途 → 输入 → 流程（判定精确/粗略 → 探索 → 提问 → 出计划）→ 产物 →
  当前项目实例 → 别名与下一层 → 坑。
- **必须替换**：“登录页”“/forgot-password”只是占位，教程里要换成当前项目真实页面/路由/组件；
  不确定就继续用 README / `git log` / codegraph 确认，别照抄示例。

## 第 0 步：codegraph 前置检查

- 会话里有 `codegraph_status` 就调用它确认索引；**没有这个工具**就用 `codegraph_explore`
  带 `projectPath` 做等价检查（能返回当前项目的符号/文件即视为可用）。
- `projectPath` 指向当前工作目录；**默认项目不是当前仓库时必须带**，否则查的是别的仓库。
- 项目确实没有 `.codegraph/`（索引未初始化）→ 立即停止，要求用户运行 `codegraph init -i`
  后重试，不得用 grep/read 绕过探索。

## 第 1 步：判定模式（精确 / 粗略）

把用户的需求描述按信息完整度分成两档：

| 特征 | 模式 |
|---|---|
| 行为、样式参照、跳转链接、端侧（云机/浏览器）、字段名等细节齐全，描述都是确定性表达 | **精确模式** |
| 信息不全，或含有"我想""大概""类似""考虑"等不确定/探索性表述 | **粗略模式** |

> 混合描述按较粗的一档处理（宁可多问一轮，不要替用户拍板方向）。

## 第 2 步：探索阶段（按 SKILL.md §3 选路下发）

按 SKILL.md §3「子代理规范」选路，**整轮只走一套，禁止混用**。下文把 Team 成员、
explore 子代理与 native 子代理统称**探索成员**：

1. **Agent Teams 可用**（会话有 `wait_agent` 且 `team_task_create`）→ 优先用 Agent Teams：
   每个探索方向 `spawn_teammate` 一个 fresh 成员，任务写清范围与要回答的问题；用 `wait_agent`
   等结果，缺信息用 `send_message` 追问。
2. **Team 不可用** → 回退：会话有 `subagent_explore` 就优先用它做只读探索（只允许 codegraph
   工具、快速模型）；没有则用 native `subagent`（不传 `run_in_background`，调用立即返回 child id，
   结果以完成通知回到对话）。
3. 两样都没有 → 主会话自己探索，不硬造委派。

涉及多个模块/多条链路时，**一次并行下发多个探索成员**，按模块切分任务，各自输出符号/文件/调用链/影响面，
不下结论、不给修改方案；结果用 `send_message` 回传 lead（native 以完成通知回传）。若探索结果提示
codegraph 未初始化，停止并按第 0 步处理。

- **精确模式**：
  1. 用探索成员定位需求涉及的所有文件、入口、现有类似实现（用户给了参照样式就找参照实现）。
  2. 基于探索结果整理出大致修改方案。
  3. 把方案里**无法从代码确定、必须用户拍板**的点整理成问题清单。

- **粗略模式**（两轮提问）：
  1. **第一轮**：先用探索成员做一次轻量探索（确定需求大概落在哪些模块、
     有哪几个可行方向、初步遇到哪些不确定点），然后向用户提问确定大概方向。
  2. 拿到第一轮答复后，**带着结论再探索**：并行下发多个探索成员深挖选定方向，确定大致修改方案。
  3. 和精确模式一样，把剩余不确定点整理成问题清单，进行第二轮提问（只问细节，不重复问方向）。

## 第 3 步：提问阶段

按 lignting skill 的"提问规范"执行：
- 优先 `ask_user_question`，每个问题带选项，推荐项放第一位；
- 每轮 ≤6 题：>6 拆两轮、>12 拆三轮，以此类推；
- 只问问题清单里的点；已在需求里明确的信息绝不重复问。

## 第 4 步：输出计划

所有问题确认后，直接向用户输出完整计划，包含：

1. **需求完整描述**：用户原话 + 确认后的细节，整合成无歧义的需求陈述
   （含端侧、参照、链接、验收要点）。
2. **完整修改计划**：
   - 按子系统/文件分组列出改动；
   - 每个改动点：文件、大致位置、改动内容、改动原因；
   - 边界情况与失败场景；
   - 明确不做的事（防止顺手改无关代码）；
   - 需要同步双端（云机/浏览器）或新增字段覆盖层级的，显式列出。

计划输出后等待用户确认；确认后才进入编码，编码遵循最小改动原则。
