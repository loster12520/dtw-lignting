# lignting discussion —— 大需求详细化讨论（/lt-discussion、/ltds）

目标：用户给一条**大需求**（可能带链接/参照/字段/端侧等细节），agent **不急着写方案**，
先探索验证可行性 → 提问敲定关键分歧 → 最后输出一份**可直接开工的完整方案文档**。
产出文档结构对齐 `rpa-element-adapter/doc/plan2/README.md`（v2 定稿的样式）。

> 与 plan 的区别：plan 面向"改一个明确功能"，discussion 面向"一整条大需求/大重构"，
> 必须先把可行性摸清、把互斥分叉拍板，再落成多阶段方案文档，而不是直接给修改点列表。

## 第 0 步：codegraph 前置检查

调用 `codegraph_status`。未初始化（项目无 `.codegraph/`）→ 立即停止，要求用户运行
`codegraph init -i` 后重试，不得绕过探索。

## 第 1 步：现状探索 + 可行性验证（先验证可行性，再谈方案）

- 用 `subagent_explore` 工具并行探索（它只允许 codegraph 工具、快速模型；
  若它告警 codegraph 未初始化，停止并按第 0 步处理）。涉及多个模块/多条链路时，
  **一次并行开多个 `subagent_explore`**，按模块切分，各自只输出符号/文件/调用链，不下结论。
- 用户给了参照（链接/样式/字段/端侧）就找参照实现一并探索。
- 探索后输出**「现有能力清单」**，每项附文件或符号依据：

| 类别 | 含义 | 举例格式 |
|---|---|---|
| 直接复用 | 现有代码/链路可直接支撑新需求 | `XPathFinder.kt`（符号 `find`）已实现… |
| 需新增 | 现状完全没有、必须新写 | 无 execute 模式入口，需新增 `CustomTaskRunner` |
| 有风险 | 复用或改造会踩坑的点 | `ResolveProcessor` 5179 行，被 `BaseAccessibilityService` 强依赖，删除有风险 |

> 若探索发现需求**不可行或代价远超预期**，先如实汇报并给替代方向，再进入提问，不硬做。

## 第 2 步：识别关键分歧点并提问

从探索结果中整理出**互斥分叉**（只能二选一或多选一的点），常见类别：

- **架构位置**：能力放 App 侧 / 宿主侧 / 服务端？
- **旧能力去留**：与新模式冲突的旧模式/模块是保留、共存还是彻底删除？
- **智能来源**：交互式 agent 兜底、确定性自动化脚本、还是两者分工？
- **数据契约细节**：任务/请求字段、schema、命名、默认值、校验规则？
- **执行语义**：串行/并行、失败重试策略、版本管理方式？

提问规范（遵守 lignting skill 公共约束）：

- 用 `ask_user_question`，每个问题带选项，**推荐项放第一位**；
- **每轮 ≤6 题**：>6 拆两轮、>12 拆三轮，以此类推；
- **只问必须拍板的点**；需求里已明确的信息绝不重复问；
- 每题选项要能直接映射到文档结论摘要表的一行（方便第 3 步落表）。

## 第 3 步：按决策输出完整方案文档

按决策逐项落盘，**文档结构逐节对齐 `rpa-element-adapter/doc/plan2/README.md`**：

1. **结论摘要表**：每条决策一行（项 | 结论），可直接对应第 2 步的每个问题。
2. **背景与目标 + 边界**：目标一句话说清；**边界 = 明确不做的事**。
3. **总体架构图**：mermaid flowchart，分模块/分端，标注数据流向与关键闭环。
4. **数据契约 / Schema**：字段表（字段 | 含义 | 默认 | 约束）+ 一份完整示例 json。
5. **分模块设计**：新增 / 保留 / 删除清单；删除项注明**依赖闭包校验原则**
   （先 grep 生产者/消费者确认无不可满足引用，再分批删、每批编译验证）。
6. **关键流程**：主流程编号步骤；**失败与证据**（失败语义、证据包内容与路径）；
   **模板 / 版本管理约定**（清空规则、时间戳版本文件、回退、重跑策略）。
7. **日志与产物规范**：固定日志行表（含义）+ 产物目录清单。
8. **分阶段计划 Phase 0..N**：每阶段必须写「**需求 / 测试方向 / 验收标准**」三行；
   每阶段可独立验证，**前序验收通过才进下一阶段**。
9. **交付物与验收标准**：交付物清单 + 可执行的验收条目（编号列）。
10. **风险与待办**：表格（# | 风险 | 缓解），待办跟进项单独列出。
11. **附录**：示例 json / 配置 / 命令样例。

落盘规则（遵守公共约束 #5）：

- **默认先输出到对话**，并询问用户保存路径；
- 若用户已给出目录（如 `doc/plan/`），直接落盘为该目录下带时间戳的文件，并告知路径；
- 落盘后把文档内容也同步输出到对话。

## 第 4 步：收尾

1. 确认文档落盘路径（未落盘则再次询问是否保存、保存到哪）。
2. 若用户表示后续要开工，给出可复制的**「实现交接提示词」**要点：
   - 引用文档绝对路径；
   - 指明从第 8 节哪个 Phase 开始、按什么顺序推进；
   - 指明验收基准（编译/单测/真机命令）与「每阶段验收通过才进下一阶段」的纪律；
   - 示例：`请按 <文档路径> 执行 Phase 1：先做依赖闭包分析…（引用第 8 节）`。
