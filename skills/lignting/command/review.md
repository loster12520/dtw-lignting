# lignting review —— 代码审查（/lt-review、/ltrv）

纯审查角色：**不修改任何代码**。支持 `low` / `middle` / `high` 三档（无 max）。

## 输入

- **可选**：级别 `low|middle|high`、审查范围描述（目录/文件/改动名）、保存路径。
- **附件也算输入**：截图、设计稿、报错日志、diff 文件可直接附；**只有附件、没有文字也算有输入**。
- **别名**：`/lt-review`、`/ltrv` 等价。
- `/ltrv` 无参数：非首次（`<项目根>/.lignting/.cr-state.json` 存在）直接按默认 `middle` +
  自动检测开审；首次先出小教程（见下）。

## 空输入处理（先于第 0 步）

**触发条件**：只有命令本身，没有文字、也没有附件。先做一次只读判断：

- `<项目根>/.lignting/.cr-state.json` **存在且可读（非首次）** → **不出教程**，先做
  第 0 步 codegraph 检查，再按第 1 步默认（`level=middle`、`scope=自动检测`）进入审查。
- **不存在（首次）** → 输出一份小教程，然后停下。**读取/解析失败 → 按首次处理**。

教程规则：

- **不进入后续流程、不做流程级代码探索、不提问、不写文件、不建目录**，也不问“要不要开始”。
- 按**当前项目真实文件/模块**重新组织，不复述种子案例里的示例名字。
- 动笔前最多花 3 步摸清项目：读 `README.md` / `package.json` / 最近 `git log -5` / 顶层目录结构。
  结构类查询用 codegraph，调用带 `projectPath`；**默认项目不是当前仓库时必须带**。
  本步不受第 0 步强制检查约束：没有索引就用这些轻量材料确认项目轮廓，不要卡在初始化。
- 教程必须覆盖：**用途 / 输入 / 流程 / 产物 / 当前项目实例 / 别名与下一层 / 3–5 条坑**。
  教程要讲清首次/非首次的差别：首次带上范围或附件，之后可直接敲 `/ltrv`。
- 末尾给一句**可复制的下一步示例**（命令 + 一条具体范围），不要用提问收尾。

## 小教程种子案例（只作结构种子）

- **场景**：刚改完一处登录限流逻辑，想按 middle 档审一遍。
- **用户可能怎么问**：`/ltrv 重点看安全，范围是刚才的限流改动`。
- **产出**：`.lignting/doc/review/YYYYMMDD-HHmmss-cr-report.md` + 对话内报告
  （PASS/FAIL、`文件:行`、🔴/🟡/🟢 分级 findings）。
- **结构种子**：用途 → 输入 → 流程（参数/状态 → 范围检测 → 状态目录 → 并行审查 → 合并保存）→
  产物 → 当前项目实例 → 别名与下一层 → 坑。
- **必须替换**：“登录限流”只是占位，教程里要换成当前 `git diff` 里的真实文件/目录；
  首次/非首次的默认档位与 `.cr-state.json` 的作用要写清。

## 第 0 步：codegraph 前置检查

- 会话里有 `codegraph_status` 就调用它确认索引；**没有这个工具**就用 `codegraph_explore`
  带 `projectPath` 做等价检查（能返回当前项目的符号/文件即视为可用）。
- `projectPath` 指向当前工作目录；**默认项目不是当前仓库时必须带**，否则查的是别的仓库。
- 项目确实没有 `.codegraph/`（索引未初始化）→ 立即停止，要求用户运行 `codegraph init -i`
  后重试。

## 第 1 步：参数解析

> `/ltrv` 先看《空输入处理》：无文字且无附件时，按首次/非首次规则决定出教程还是直接开审。
> 首次/非首次的唯一判据：`<项目根>/.lignting/.cr-state.json` 是否存在且可读。

```
/ltrv（无文字、无附件）            → 非首次: level=middle, scope=自动检测（直接开审）
                                      首次:   输出小教程，进入审查前停下
/ltrv low|middle|high              → 指定级别（显式级别优先于默认）
/ltrv high 浏览器下发                → level=high, scope="浏览器下发"
/ltrv 浏览器下发页面                 → level=middle, scope="浏览器下发页面"
scope 含"放到/保存到/输出到"后跟路径  → 提取 savePath（默认保存见第 5 步）
均不匹配                            → scope 整体作为搜索描述
```

> **硬规则（状态文件）**
>
> - **存在且可读 = 非首次**：无参数默认 `level=middle` + `scope=自动检测`，
>   **禁止**反问用户级别，**禁止**要求用户重敲 `/ltrv middle`，直接按 middle 执行；
>   用户显式给了参数就按参数。
> - **不存在 = 首次**：无参数 → 走《空输入处理》输出教程；带了文字/附件 → level 缺省 middle，
>   按所给 scope/附件继续。
> - **存在但读取/解析失败 → 按首次处理**：不阻塞，也不把脏状态当成默认 middle。

## 第 2 步：范围检测

1. 有 scope 描述 → 有 `codegraph_search` 就用它，没有就用 `codegraph_explore` 带
   `projectPath` 查结构；grep 只用于定位文件字面位置，不替代结构查询；
2. 无 scope → 读 `.lignting/.cr-state.json`（存在则对比当前 git diff：
   新修改文件与上次 `reviewedFiles` 无重叠 → 只扫新文件；有重叠 → 全额扫）；
3. 无状态文件 → `git diff --staged` + `git diff`（未提交代码）；无 diff →
   输出 "❌ 没有可审查的代码：当前对话未修改文件，且工作区无未提交更改。" 结束。

## 第 3 步：状态目录初始化（幂等，用户无感）

在创建 `.lignting/` 下任何文件**之前**，按顺序执行：

1. 检查 `<项目根>/.git/info/exclude` 是否存在，不存在则创建（git 本地排除文件，不影响仓库）；
2. 若其中没有 `.lignting/` 行，追加 `.lignting/`（屏蔽整个 lignting 文件夹）；
3. 创建 `.lignting/` 目录（报告目录 `.lignting/doc/review/` 按需创建）；
4. 用 `git check-ignore .lignting/` 验证已被忽略。

全程静默完成，不向用户解释，不要求用户改任何 git 配置。

## 第 4 步：按档位并行审查（Agent Teams 优先）

按 SKILL.md §3 选路，**整轮只走一套，禁止混用**：

- **Agent Teams 可用**（会话有 `wait_agent` 且 `team_task_create`）：
  low / middle / high = **1 / 3 / 8 路**，每路 `spawn_teammate` 一个 **fresh** 成员，
  同一档位一次并行启动；成员结果用 `send_message` 回 lead，收齐后合并。
  - **high 的 8 路正好占满成员上限**：已有成员先复用（同方向沿用已建成员），不够再分批启动
    （例如先 4 路、收口后再 4 路），不要超上限硬开。
  - 每个成员的 prompt 必须**自包含**（不依赖主对话上下文）、**只读**（明确写“不修改任何代码”），
    并要求：**先给 `结论：PASS|FAIL`**，再列 `文件:行` + 🔴/🟡/🟢 分级 findings；
    无问题的维度写“✅ 未发现明显问题”并判 PASS。
- **Team 不可用** → 回退 native `subagent`：每路一个子代理，**不传 `run_in_background`**
  （调用立即返回 child id，结果以完成通知回到对话），收齐通知后合并。
- 两样都没有 → 主会话自己按下方模板逐维度审查；但若主会话就是本次改动的实现者，
  必须明说无法满足“审查者≠实现者”，请用户启用委派后再审。
- 各成员/子代理的结构查询一律用 codegraph（遵守 lignting 公共约束）。
- 每个 prompt 从下方模板内联，替换 {fileList}（审查范围文件清单 + 简要变更说明）。
- **审查者≠实现者**：实现过本次改动的人不参与本档审查；每路成员/子代理必须是 fresh 上下文。

> **判定口径**：出现任一 🔴/🟡 → `FAIL`；只有 🟢 或没有问题 → `PASS`。
> 结果回传 lead：Teams 成员用 `send_message`；native 子代理以最终输出/完成通知回传。

### low —— 档 1（1 路：1 个成员/子代理）

```
你是代码审查员（档1）。只检查以下文件的正确性、一致性、完整性与安全性，不修改任何代码：
{fileList}
- 正确性：逻辑错误、边界条件、异步时序、空值/越界、错误处理缺失
- 一致性：与周边代码风格/模式一致、命名统一
- 完整性：改动自洽、有无遗漏配套修改（类型/表单/回填/日志映射等）
- 安全性：注入、敏感信息泄露、权限绕过、XSS/CSRF 等红线
输出格式：先给 `结论：PASS|FAIL`；每个问题给出 `文件:行` + 🔴Critical / 🟡Important /
🟢Suggestion + ❌/✅ 前后示例；没有问题的维度明确写"✅ 未发现明显问题"。
完成后把结果回传给 lead（Teams 用 `send_message`；native 子代理直接作为最终输出返回）。
```

### middle —— 档 2（3 路并行：可读性 / 安全性 / 性能）

通用模板（每路替换 {方向} 为下表对应维度，并只审该维度）：

```
你是代码审查员（档2-{方向}）。基于以下未提交改动审查，不修改任何代码：
{fileList}
请用 git diff 获取变更内容，按 {方向} 维度逐条审查，先给 `结论：PASS|FAIL`，
每个问题给出 `文件:行` + ❌/✅ 前后示例，按 🔴Critical / 🟡Important / 🟢Suggestion 分级。
没有问题的维度明确写"✅ 未发现明显问题"。
完成后把结果回传给 lead（Teams 用 `send_message`；native 子代理直接作为最终输出返回）。
```

| 方向 | 审查要点 |
|---|---|
| 可读性 | 命名是否清晰一致；函数是否过长/职责单一；嵌套层级是否合理(≤3)；注释是否准确；魔数/魔法字符串是否应抽常量；是否与代码库既有模式一致 |
| 安全性 | 注入风险；敏感数据泄露(日志/存储/前端)；鉴权绕过；外部输入校验；XSS/CSRF |
| 性能 | 冗余计算；循环可优化点；重复请求；渲染循环内昂贵操作；内存泄漏(未清理 listener/timer/subscription)；异步竞态；N+1 查询；防抖/批处理 |

### high —— 档 3（8 路并行）

档 2 的 3 路（可读性/安全性/性能）+ 以下 5 路，一次并行启动，共 8 路：

| # | 方向 | 审查要点 |
|---|---|---|
| 4 | 基础安全 | 依赖安全配置、超时/重试、敏感配置项、密钥硬编码、第三方调用面 |
| 5 | 架构一致性 | 是否符合分层/既有模式；是否引入不必要抽象或破坏分层；跨文件影响与调用方 |
| 6 | 扩展性与可维护性 | 重复代码、硬编码、是否复用项目既有工具/组件、可配置性 |
| 7 | 性能与并发风险 | 循环、锁、IO 影响、并发读/写冲突、批处理与节流 |
| 8 | 影响范围分析 | 调用链影响、依赖此改动的其他模块、回滚可行性、回归风险 |

prompt 模板同档 2，替换 {方向} 为上表对应行。

## 第 5 步：报告合并与保存

- 收集所有成员/子代理的结果（`send_message` 回传或完成通知，不要漏掉任何一个），按模板合并：

```markdown
## 🔍 Code Review 报告
**审查级别：** {level}
**审查范围：** {scope 描述 或 "未提交代码 (N 个文件)"}
**扫描文件：** N 个
### 📋 变更概览（文件 | 改动概述）
### 🔍 详细审查（每个子代理一节：Agent N: {方向}）
### 🎯 修复方案（优先级 P0/P1/P2 | 问题 | 文件 | 建议方案）
### ⭐ 综合评分（正确性/一致性/完整性/安全性 × 各 Agent → 综合）
综合规则：取各 agent 最低分作基准；多 agent 交叉验证一致的维度 +0.5 星；有分歧标注"⚠️ 有分歧"。
```

- **默认保存**：`.lignting/doc/review/YYYYMMDD-HHmmss-cr-report.md`
  （先确保 `.lignting/` 已被 exclude，见第 3 步；保存后告知用户路径），
  同时把报告内容输出到对话。语言默认中文（代码/标识符保留原文）。
- 更新 `.lignting/.cr-state.json`：`lastReviewAt` / `lastCommitHash` / `reviewedFiles`。

## 注意事项

1. 绝不修改任何代码。
2. 同一档位的所有路一次并行启动（多个调用）。Agent Teams 优先，见第 4 步开头；
   Team 不可用才回退 native `subagent` 且**不传 `run_in_background`**。结果以 `send_message` /
   完成通知回到 lead，收齐后再合并；high 8 路占满上限时先复用已有成员或分批。
3. low 档检测到 >5 个文件 → 提示用户是否升级 middle。
4. 审查范围必须在报告开头明确标注。
5. 审查完成必须更新 `.lignting/.cr-state.json`。
