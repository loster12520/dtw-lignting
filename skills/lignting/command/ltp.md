# lignting Pentacles —— 星币层 · 细节敲定（/ltp）

目标：吃下一个阶段，产出**分轮详细计划**——具体动哪、按什么顺序动、怎么验证没动坏。
供下一层（`/ltw`）执行。

> **只细化即将执行的那一轮，最多前瞻一轮。**
> 细分计划有保鲜期。把后面几轮全细化了，等真跑到那一轮，计划早过期了，
> 而执行者还会碍于"计划里写了"而照做——那比没有计划更糟。

## 输入

- 上游阶段表（通常 `.lignting/<feature>/phases.md`）
- **要细化的阶段号**（用户指定；未指定时问清，不要默认全做）
- 该阶段涉及的真实代码
- 本层对话记录 `phase-<n>/round-<m>.dialogue.md` 与上一轮执行报告
  `phase-<n>/round-<上一轮>.report.md`（若有）
- **可以随命令附图片 / 文件**：阶段表片段、设计稿、报错日志、旧计划都能直接附在命令后面
  （例如 `/ltp 按这份阶段表细化 Phase 1 <附文件>`）。附件内容算输入的一部分，不要让用户再复述。
- **只有附件、没有文字也算输入**：从附件里定位阶段与范围，按第 1 步开始；**不得当空输入处理**。
- **空输入**：只有命令本身，既没有文字也没有附件，才算空输入——按下面「空输入处理」先出小教程。
- **`roadmap.md` 不是输入**：它是人读总计划视图（格式见
  [roadmap-format.md](../references/roadmap-format.md)），冲突以 `phases.md` / round 文档为准。
- **别名**：`/ltp` = `/lt-pentacles`。注意 **`/ltpl` 是另一个命令（轻量规划），不是本命令别名**。

## 空输入处理（先于第 1 步）

**判定**：空输入 = 只发了 `/ltp`，**既没有文字、也没有附件**。给了文字或附件就是有效输入，
走正常流程。

空输入时**不进入正式流程**（本文件从第 1 步开始）：不做流程级代码探索、不提问、不排改动顺序、
不改任何文件——直接在对话里输出一篇**本命令的小教程**。

教程不是写死的模板，**由模型按当前项目现场重新组织**，例子必须是这个项目里真实存在的文件/模块。

**先确认项目（最多 3 步，做完就写）**：

1. 读 `README` / `package.json`（或其他语言的等价清单），确认项目是什么、怎么构建与检查。
2. 看最近几次 `git log --oneline -10`，了解当前在做什么。
3. 需要结构信息时用 codegraph 查（`codegraph_explore`，带 `projectPath`），或列一下顶层目录。

**教程结构（顺序固定，内容按项目填）**：

1. **用途与适用** —— 吃一个阶段、产出分轮详细计划；方向未定回 `/lts`，只需排期走 `/ltc`，
   单点小改走 `/ltpl`。
2. **输入怎么给** —— 需要阶段表、阶段号与该阶段真实代码，怎么随命令附图片/文件，什么算空输入。
3. **分步流程与判断标准** —— 确认细化哪一轮 → 依赖闭包（codegraph 查生产/消费方）→
   先判断 + 3–4 问 + 3–5 行暂定大纲 → 分轮排序（中间态坏得最少，判据是"每步做完还能编译、
   还能验证"）→ 每步三样（改动内容/回滚点/验证命令）→ 计划文档 → **用户确认后才执行**。
4. **产物与落盘路径** —— 默认 `.lignting/<feature>/phase-<n>/round-<m>.md`（含「核心目的」）；
   落盘后追加 `round-<m>.dialogue.md` 并更新 `roadmap.md` §3/§1/§5/§6；只细化即将执行的那一轮。
5. **当前项目实例** —— 用刚确认的真实文件/符号举一例，说明"先加后删"的顺序在**这个项目**里长什么样。
6. **别名与下一层** —— 列出别名；写清计划确认后接 `/ltw .lignting/<feature>/phase-1/round-1.md`。
7. **常见坑（3–5 条）** —— 本层最容易犯的错（一次细化多个阶段、"检查是否正常"式验证、
   排出的顺序让中间态编译不过等），每条给一句避法。

教程直接在对话里输出。**不写文件、不建目录、不问"要不要开始"**——末尾给一句可直接执行的示例命令即可。

## 小教程种子案例（只作结构种子）

> 以下是**结构种子**，只示范教程该长成什么样；**输出教程时必须替换为当前项目的真实文件/模块，不得照抄**。

- **场景**：阶段表里的 Phase 1 是"把配置读取抽成独立模块"，要落成一轮一轮、每步都能验证的改动。
- **用户可能怎么问**：`/ltp .lignting/config-layer/phases.md Phase 1`（或只发 `/ltp` 的空输入）。
- **产出**：`round-1.md`——核心目的、本轮范围与明确不做、依赖闭包结论、先加后删的改动顺序
  （每步含改动内容/回滚点/真实可跑验证命令）、验收标准细化、边界情况，收尾推荐
  `/ltw .lignting/config-layer/phase-1/round-1.md`。
- **教程里必须替换**："配置读取模块"和它的调用方要换成当前项目真实符号，
  验证命令要用该项目 `package.json` / 构建脚本里真实存在的命令。

## 局部例外

- `codegraph` 门槛**不适用**于本层的放宽——本层必须走真实结构。按公共约束执行前置检查，
  未初始化则要求用户先 `codegraph init -i`。

## 第 1 步：确认要细化哪一轮

- 用户指定了阶段 → 直接做。
- 用户想"把整个阶段表都细化了" → **只做第一个阶段**，并说明理由（保鲜期），
  把其余的留给后续按需调用。
- 上一轮的 `/ltw` 报告（`phase-<n>/round-<上一轮>.report.md`）显示有偏离 → 先读那份报告，
  **按现实调整**，不要照抄上游阶段表。

## 第 2 步：依赖闭包校验（改动前强制）

涉及删除、替换、搬迁的改动，**先做依赖闭包分析**再谈顺序：

- 用 codegraph 找出该符号/模块的**所有生产者与消费者**（`codegraph_callers` /
  `codegraph_impact`）。
- 逐个确认：删除后有没有不可满足的引用？
- 有跨端（云机/浏览器）或跨层调用时，**两端都要查**。

闭包没查清就排顺序，等于排了个假计划。

## 第 3 步：先判断 + 3–4 问 + 3–5 行暂定大纲

排改动顺序之前，先把"这一轮大概怎么切、还缺什么信息"摆到用户面前。**这一步不展开完整计划**。

### 3.1 先给判断与证据

先回答"这一轮该怎么切、顺序大概怎么排"：判断 + 依据（依赖闭包结论、上游核心验收标准、
风险）+ 不确定点（标 `[猜想·待验证]`，给验证路径）。不要一上来就抛问题或直接排步骤。

### 3.2 问 3–4 个最核心的问题（四段式）

规则见 `SKILL.md` §4.2：**每轮 3–4 问，硬上限 4**；真正阻塞不足 3 个不凑数；超过 4 个列
"待问清单"下一轮再问。每个问题四段：**背景 / 问题 / 你为什么这么考虑 / 推荐答案**。

- **开放问题**（还在长、不是互斥选择）：普通对话问，**不给选项**；推荐答案写成"我倾向 X，因为…"。
- **分叉决策**（两边都通 + 只能选一 + 选错返工）：用 `ask_user_question`，**推荐项放第一位**，
  四段写进 `question` 字段（换行分段），`header` 只放短标签（≤6 字）。
- 引用上游文档、上一轮 report、对话记录里的结论时带回指链接。
- **不播报层名/相名**，讨论重点变化时用自然过渡（已定 / 未定 / 本轮要做什么）。

### 3.3 先给 3–5 行极简暂定大纲

问题后面附一份**极简暂定大纲**：只写轮次名 + 一句核心目的，3–5 行，开头标注
"**暂定，待确认后展开**"：

```markdown
暂定大纲（待确认后展开）：
- R1 <轮次名> —— <核心目的：为什么非做不可>
- R2 <轮次名> —— <核心目的>
- R3 <轮次名> —— <核心目的>
```

它只是让用户看清"你打算怎么切轮"的草图：**不写改动顺序、验证命令、文件细节**，
也**不算分轮计划**。用户拍板或改完后，才进入下一步展开。

**没有 roadmap 时**：先按 [roadmap-format.md](../references/roadmap-format.md) 建最小框架
（头部 + §1 + 空节纯文字「待填充」），再继续讨论；**不要**因为缺 roadmap 阻塞，也不要因此
要求用户先补跑别的命令（输入够就继续）。

## 第 4 步：分轮，并排出改动顺序

**拆成"轮"**：一轮 = 一次可交付、可验收的工作量（大致一次会话能干完的规模）。

排序的判据只有一条：

> **中间态坏得最少。**

具体做法：

- 如果按最自然的顺序改，中间会出现"三天编译不过"——**那是分解错了**。
  调整顺序，或插入一个过渡态（临时保留新旧两条路、加一层适配垫片），
  让每一步之后系统都处于可编译、可验证的状态。
- 大改动优先考虑**先加后删**：先引入新路径并让它和旧路径并存，验证通过后再删旧。
- 顺序里要标出**不可并行的步骤**。

排完顺序自检一遍：**每一步做完，系统还能编译吗？还能验证吗？**
任何一步答"不能"，回去重排。

## 第 5 步：给每一步配三样东西

每个步骤必须有：

1. **改动内容** —— 文件、大致位置、改什么、为什么改。
2. **回滚点** —— 这一步之后能不能退、退到哪、退的代价是什么。
   不可回滚的步骤要**显式标注**（比如数据迁移、删除类操作）。
3. **验证命令** —— 一条真能跑的命令（编译 / 单测 / 真机命令），
   不是"检查是否正常"。

**验证粒度原则**：不攒到最后跑一次。每一步自带验证，坏了好定位。

## 第 6 步：输出计划文档

章节清单：

1. **核心目的** —— 为什么这一轮非做不可（不做会阻塞什么 / 为后续轮次消除什么风险）；
   一句话，不等于「本轮范围」。
2. **本轮范围** —— 对应上游哪个阶段；**明确不做什么**（防顺手改无关代码）。
3. **依赖闭包结论** —— 第 2 步的产出：受影响的生产者/消费者清单。
4. **改动顺序与步骤** —— 每步含：改动内容 / 回滚点 / 验证命令。
   用表格或有序列表，**顺序必须是可执行的**。
5. **验收标准细化** —— 把上游阶段的「核心验收标准」展开成**可执行条目**：
   每条给编号 + 具体命令 + 期望结果。这一节是 `/ltw` 的自测依据。
   **不得偏离上游核心验收标准的意图**——展开，不是替换。
6. **边界情况与失败场景** —— 什么情况下会失败、失败时怎么处理。
7. **与上游的偏离** —— 见 [plan-doc-format.md](../references/plan-doc-format.md)。

**核心目的 ≠ 本轮范围**：范围回答"动哪里"，核心目的回答"为什么现在必须动"；
写不出就回头看看这一轮是不是切错了。

写法遵守 [plan-doc-format.md](../references/plan-doc-format.md)。

## 落盘与收尾

1. 先在对话输出让用户过目；计划必须**确认后才执行**（公共约束）。
2. 问路径，默认建议 `.lignting/<feature>/phase-<n>/round-<m>.md`。
3. 落盘后追加本轮对话记录 `phase-<n>/round-<m>.dialogue.md`（按
   [dialogue-log-format.md](../references/dialogue-log-format.md)：本轮的问题、判断、
   被否决方案、待验证猜想都记进去；只追加，不写相名/层名标签）。
4. 落盘后更新 `.lignting/<feature>/roadmap.md`（按
   [roadmap-format.md](../references/roadmap-format.md)；先读最新全文、按 heading 用 edit 精确改）：
   - §3 当前轮**整块替换**：轮次号 / 核心目的 / 要做什么 / 明确不做 / 验收 / 改动顺序 / 回滚 /
     链接（计划 + 验收标准细化锚点）；上方标注「派生自计划原文 · 同步于 <日期>；冲突以计划原文
     为准」；旧轮不搬运（canonical 在 round 文档，历史由 §4 指向）；
   - §1 现状行改成指向本轮的位置指针；§5 只追加**轮次组**决策（链到
     `round-<m>.dialogue.md` 锚点）；§6 更新 `round-<m>.md`、`round-<m>.dialogue.md` 两行；
   - **不动 §2/§4**；不写完成状态；头部「最后同步」改当天；roadmap 不存在时先按格式建最小框架。
5. 落盘后写进 whatsnext 任务 `index.md` 的「文件」索引（**不要登记 roadmap**——它不是命令输入）。
6. 给一句可粘贴的下一步命令：

   ```
   /ltw .lignting/<feature>/phase-1/round-1.md
   ```

## 不要做的事

- 不要一次细化多个阶段。
- 不要写"检查是否正常"这种无法执行的验证。
- 不要排出会让中间态编译不过的顺序。
- 不要把上游的核心验收标准替换掉——只展开。
- 不要超出本轮范围顺手改无关代码。
- 不要先排步骤再补问题：先给判断 + 3–4 问 + 3–5 行暂定大纲，用户拍板后再展开。
- 不要一轮问超过 4 个问题，也不要凑数问 3 个；不要问没有推荐答案的问题。
- 不要把「暂定大纲」写成完整分轮计划（改动顺序/验证命令/文件细节都不写）。
- 不要漏掉 round 计划的「核心目的」，也不要把它写成「本轮范围」。
- 不要忘记落盘 `round-<m>.dialogue.md` 与 roadmap §3/§1/§5/§6（且不动 §2/§4）。
