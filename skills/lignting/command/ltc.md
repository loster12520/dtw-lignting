# lignting Cups —— 圣杯层 · 方案细化（/ltc）

目标：吃下方向文档，产出**阶段表 + 每阶段的核心验收标准**，供下一层（`/ltp`）逐轮细化。

> **本层的主要工作是分阶段，和核心验收标准。**
> 核心验收标准的作用是**引导下游**——它定义"这一步做成什么样才算成"，
> `/ltp` 再据此细化出具体的、可执行的验收条目。

## 输入

- 上游方向文档（通常 `.lignting/<feature>/direction.md`）
- 上游对话记录 `direction.dialogue.md` 与本层对话记录 `phases.dialogue.md`（若有，接上未完成的分歧）
- **可以随命令附图片 / 文件**：方向文档、评审意见、截图、旧素材都能直接附在命令后面
  （例如 `/ltc 按这张图的结构排阶段 <附截图>`）。附件内容算输入的一部分，不要让用户再复述。
- **只有附件、没有文字也算输入**：从附件里定位方向与约束，按第 1 步开始；**不得当空输入处理**。
- **空输入**：只有命令本身，既没有文字也没有附件，才算空输入——按下面「空输入处理」先出小教程。
- **`roadmap.md` 不是输入**：它是人读总计划视图（格式见
  [roadmap-format.md](../references/roadmap-format.md)），冲突以 `direction.md` / `phases.md` 为准。
- **别名**：`/ltc` = `/lt-cups`，行为完全一致；其他写法以 `SKILL.md` 路由表为准。

用户未给路径时问清；给了路径直接读。**同时读上游的对话记录**——只看结论不看理由，
很容易把已否决的方案又搬回来。

按 [whatsnext-bridge.md](../references/whatsnext-bridge.md) 第 0 步口径接续既有任务。

## 空输入处理（先于第 1 步）

**判定**：空输入 = 只发了 `/ltc`，**既没有文字、也没有附件**。给了文字或附件就是有效输入，
走正常流程。

空输入时**不进入正式流程**（本文件从第 1 步开始）：不做流程级代码探索、不提问、不排阶段、
不改任何文件——直接在对话里输出一篇**本命令的小教程**。

教程不是写死的模板，**由模型按当前项目现场重新组织**，例子必须是这个项目里真实存在的文件/模块。

**先确认项目（最多 3 步，做完就写）**：

1. 读 `README` / `package.json`（或其他语言的等价清单），确认项目是什么、模块怎么分。
2. 看最近几次 `git log --oneline -10`，了解当前在做什么。
3. 需要结构信息时用 codegraph 查（`codegraph_explore`，带 `projectPath`），或列一下顶层目录。

**教程结构（顺序固定，内容按项目填）**：

1. **用途与适用** —— 吃方向文档、产出阶段表 + 核心验收标准；方向还没定就先 `/lts`，
   单点小改走 `/ltpl`。
2. **输入怎么给** —— 需要方向文档（或等价材料）与对话记录，怎么随命令附图片/文件，什么算空输入。
3. **分步流程与判断标准** —— 方向复核 → 先判断 + 3–4 问 + 3–5 行暂定大纲 → 分阶段
   （每阶段可用、可独立验证、依赖少、风险前置、不横切）→ 写核心验收标准（架构层；
   用"删掉它 `/ltp` 会不会走偏"自检）→ 待决问题归属 → 阶段表 → 落盘。
4. **产物与落盘路径** —— 默认 `.lignting/<feature>/phases.md`，每阶段带「核心目的」；
   落盘后追加 `phases.dialogue.md` 并更新 `roadmap.md` §2/§1/§5/§6；一次只推荐一个阶段给 `/ltp`。
5. **当前项目实例** —— 用刚确认的真实文件/模块举例子：在**这个项目**里阶段边界大概画在哪。
6. **别名与下一层** —— 列出别名；写清阶段表落盘后接 `/ltp .lignting/<feature>/phases.md Phase 1`。
7. **常见坑（3–5 条）** —— 本层最容易犯的错（核心验收写成"功能可用"、方向没复核就排期、
   一次细化多个阶段等），每条给一句避法。

教程直接在对话里输出。**不写文件、不建目录、不问"要不要开始"**——末尾给一句可直接执行的示例命令即可。

## 小教程种子案例（只作结构种子）

> 以下是**结构种子**，只示范教程该长成什么样；**输出教程时必须替换为当前项目的真实文件/模块，不得照抄**。

- **场景**：已有方向文档定了"先抽配置层、再迁移调用方"，需要拆成几个能独立验收的阶段。
- **用户可能怎么问**：`/ltc .lignting/config-layer/direction.md`（或只发 `/ltc` 的空输入）。
- **产出**：`phases.md`——阶段总览、依赖图、分阶段详述、待决问题归属、与上游的偏离；
  每阶段带「核心目的」+ 1–3 条架构层核心验收标准；收尾推荐
  `/ltp .lignting/config-layer/phases.md Phase 1`。
- **教程里必须替换**："配置层"要换成当前项目真实的 feature 与模块，"迁移调用方"要换成
  该项目 codegraph 能查到的真实调用关系。

## 第 1 步：确认方向仍然成立

排期之前先做一次**方向复核**，别急着拆阶段：

- 上游的「目标与非目标」还准确吗？
- 上游的「不可逆架构契约」有没有已经过期的？
- 上游的「待决问题」里，**哪些必须在排期前解决**？

发现有站不住的地方 → 按下面「与上游的偏离」处理，**不要默默绕过**。

## 第 2 步：先判断 + 3–4 问 + 3–5 行暂定大纲

分阶段之前，先把"我打算怎么切"和"还缺什么信息"摆到用户面前。**这一步不展开完整阶段表**。

### 2.1 先给判断与证据

先回答"怎么看这条方向、大概怎么切阶段"：判断 + 依据（上游文档哪节、代码现状、风险）+
不确定点（标 `[猜想·待验证]`，给验证路径）。不要一上来就抛问题或直接排阶段。

### 2.2 问 3–4 个最核心的问题（四段式）

规则见 `SKILL.md` §4.2：**每轮 3–4 问，硬上限 4**；真正阻塞不足 3 个不凑数；超过 4 个列
"待问清单"下一轮再问。每个问题四段：**背景 / 问题 / 你为什么这么考虑 / 推荐答案**。

- **开放问题**（还在长、不是互斥选择）：普通对话问，**不给选项**；推荐答案写成"我倾向 X，因为…"。
- **分叉决策**（两边都通 + 只能选一 + 选错返工）：用 `ask_user_question`，**推荐项放第一位**，
  四段写进 `question` 字段（换行分段），`header` 只放短标签（≤6 字）。
- 引用上游文档、被否决方案、对话记录里的结论时带回指链接。
- **不播报层名/相名**，讨论重点变化时用自然过渡（已定 / 未定 / 本轮要做什么）。

### 2.3 先给 3–5 行极简暂定大纲

问题后面附一份**极简暂定大纲**：只写阶段名 + 一句核心目的，3–5 行，开头标注
"**暂定，待确认后展开**"：

```markdown
暂定大纲（待确认后展开）：
- P1 <阶段名> —— <核心目的：为什么非做不可>
- P2 <阶段名> —— <核心目的>
- P3 <阶段名> —— <核心目的>
```

它只是让用户看清"你打算怎么切"的草图：**不写技术路线、验收标准、文件改动**，
也**不算阶段表**。用户拍板或改完后，才进入下一步展开。

## 第 3 步：分阶段

阶段划分的判断标准（按优先级）：

1. **每阶段结束时系统必须是可用的**。不能出现"做完第二阶段才能跑起来"的设计。
2. **每阶段要能独立验证**——有明确信号说明这一步成了。
3. **前序依赖要少而清楚**。依赖链越短，后面改主意的成本越低。
4. **风险前置**：不确定的技术路线放在前面阶段，越早证伪越好。
5. **阶段之间不要横切**：不要出现"每个阶段都改一遍同一处"的划分。

阶段数量不设硬指标，但**明显能合并的阶段要合并**——阶段本身也有维护成本。

## 第 4 步：写核心验收标准（本层的核心产出）

每个阶段必须有核心验收标准。它不是"功能可用"这种产品层验收，而是**架构层验收**：

> **这条路线被证明可行。**

差的写法 vs 好的写法：

| 差 | 好 |
|---|---|
| 功能可用 | 抽象层能同时承载 A 和 B 两种实现（拿一个最小实现验证过） |
| 页面正常 | 中间态不影响存量功能（存量用例全绿） |
| 性能达标 | 回滚一次不需要重新构建环境 |

**自检判据**：把这条验收标准删掉，`/ltp` 会不会走偏？

- 会走偏 → 它确实在引导，是合格的核心验收标准
- 不会 → 它只是复述了阶段目标，**重写**

核心验收标准要**少而硬**：一个阶段 1–3 条。多了等于没有重点。

## 第 5 步：定待决问题的归属

上游抛下来的待决问题，逐个决定**到哪一层必须定**：

| 归属 | 判定 |
|---|---|
| 本层定 | 不定就排不出阶段 → 现在就问用户拍板 |
| `/ltp` 定 | 要靠实现细节才能判断 → 标进对应阶段，交给下游 |
| 继续悬置 | 不影响任何阶段推进 → 保留在待决清单，注明"暂不影响" |

**"哪个待决问题该在什么时候解决"本身就是本层的判断力所在**，
不要把所有待决问题都往下推，也不要全部现在逼定。

## 第 6 步：输出阶段表

章节清单：

1. **阶段总览** —— 表格：阶段 | **核心目的** | 一句话目标 | 前序依赖 | 主要风险
2. **阶段依赖图** —— mermaid flowchart，标出串行与可并行
3. **分阶段详述** —— 每阶段一小节，各含：

   | 项 | 说明 |
   |---|---|
   | **核心目的** | **为什么这一步非做不可**（不做会怎样、为后续消除什么不确定性），不等于「目标」 |
   | 目标 | 这一阶段要达成什么 |
   | 技术路线 | **走哪条路**，不是"怎么实现" |
   | **核心验收标准** | 1–3 条，按第 4 步的判据自检过 |
   | 前序依赖 | 依赖哪些阶段 / 外部条件 |
   | 主要风险 | 可能让本阶段失败的点 |

4. **待决问题归属** —— 按第 5 步的表格
5. **与上游的偏离** —— 见下

**核心目的 ≠ 目标**：目标回答"做成什么样"，核心目的回答"为什么现在非做这一步不可"；
每阶段一句话，写不出就说明这个阶段可能该合并或删掉。

**技术路线 ≠ 技术方案**：写"先抽接口再迁移"，不写"改 XxxService 的 foo 方法"。
具体的改动落到哪个文件，是 `/ltp` 的事。

写法遵守 [plan-doc-format.md](../references/plan-doc-format.md)。

## 与上游的偏离

本层**有权威**推翻上游结论（更近实现、信息更多），但必须显式记录：

- 在本文档「与上游的偏离」节里逐条列出：上游结论 / 本层结论 / 理由 / 建议。
- 偏离若影响方向层（比如否掉了上游的架构方向），**主动提示用户**建议同步修订上游文档，
  不要只在文档角落里写一行。

## 落盘与收尾

1. 先在对话输出让用户过目。
2. 问路径，默认建议 `.lignting/<feature>/phases.md`。
3. 落盘后追加本层对话记录 `phases.dialogue.md`（按
   [dialogue-log-format.md](../references/dialogue-log-format.md)：本轮的问题、判断、
   被否决方案、待验证猜想都记进去；只追加，不写相名/层名标签）。
4. 落盘后更新 `.lignting/<feature>/roadmap.md`（按
   [roadmap-format.md](../references/roadmap-format.md)；先读最新全文、按 heading 用 edit 精确改）：
   - §2 大轮次：每阶段一行（`#` / 核心目的 / 要做什么 / 1–3 条核心验收标准 / 链接），
     上方标注「派生自 phases.md · 同步于 <日期>；冲突以 phases.md 为准」；边界变更只追加；
   - §1 现状行改成指向 §2 的位置指针；§5 只追加**阶段组**决策（链到 `phases.dialogue.md` 锚点）；
   - §6 更新 `phases.md`、`phases.dialogue.md` 两行（未生成的行保持纯文字，不写死链）；
   - **不动 §3/§4**；不写完成状态；头部「最后同步」改当天；roadmap 不存在时先按格式建最小框架。
5. 落盘后写进 whatsnext 任务 `index.md` 的「文件」索引（**不要登记 roadmap**——它不是命令输入）。
6. 给一句可粘贴的下一步命令：

   ```
   /ltp .lignting/<feature>/phases.md Phase 1
   ```

   **一次只推荐一个阶段**。`/ltp` 只细化即将执行的那一轮，不要一次把后面所有阶段都细化
   ——细分计划有过期时间。

## 不要做的事

- 不要写具体文件路径、函数名、字段表——那是 `/ltp` 的活。
- 不要把核心验收标准写成"功能可用"。
- 不要跳过「确认方向仍然成立」直接排期。
- 不要把所有待决问题都推给下游。
- 不要一次推荐细化多个阶段。
- 不要先甩阶段表再补问题：先给判断 + 3–4 问 + 3–5 行暂定大纲，用户拍板后再展开。
- 不要一轮问超过 4 个问题，也不要凑数问 3 个；不要问没有推荐答案的问题。
- 不要把「暂定大纲」写成完整阶段表（技术路线/验收/文件都不写）。
- 不要忘记落盘 `phases.dialogue.md` 与 roadmap §2/§1/§5/§6（且不动 §3/§4）。
