## 小阿卡那（Minor Arcana）体系 —— 主流程

从「一个还没成形的想法」到「代码写完并汇报」的四层递进。**每层的产物是下一层唯一的输入**，
不跨层引用。命名取自小阿卡那四组牌的性格：风（思辨）→ 水（愿景）→ 土（务实）→ 火（行动）。

| 层 | 命令 | 别名 | 输入 → 产物 | 流程文件 |
|---|---|---|---|---|
| 宝剑 | `/lts` | `/lt-swords` | 想法 → 方向文档 + roadmap 框架 | `command/lts.md` |
| 圣杯 | `/ltc` | `/lt-cups` | 方向文档 → 阶段表（每阶段核心目的）+ 核心验收标准 | `command/ltc.md` |
| 星币 | `/ltp` | `/lt-pentacles` | 阶段表 + 阶段号 → 分轮计划（每轮核心目的 + 顺序/回滚） | `command/ltp.md` |
| 权杖 | `/ltw` | `/lt-wands` | 详细计划 → 代码 + 四段汇报（落 `round-<m>.report.md`） | `command/ltw.md` |

每层有**不可替代的判断力**（写死在流程文件里，否则会退化成排版工）：

| 层 | 判据问句 | 不可替代的判断力 |
|---|---|---|
| 宝剑 | 往哪走、为什么这么走 | 先判断后提问；区分开放问题与分叉决策（四相只作内部判断） |
| 圣杯 | 先做哪个、什么绝不能漏 | 阶段划分；每阶段写清核心目的；指出最核心必覆盖的能力 |
| 星币 | 具体动哪、什么顺序、怎么验证 | 每轮核心目的；改动顺序（中间态坏得最少）；依赖闭包；回滚点 |
| 权杖 | 做完没有、跟计划差在哪 | 偏离必须明说；汇报末段是回灌通道 |

**核心目的**：`/ltc` 的每个阶段、`/ltp` 的每一轮都必须写清「核心目的」——**为什么这一步
非做不可**；它不等于“目标”或“要做什么”（目标回答做成什么样，核心目的回答为什么现在必须做）。

## 讨论规范：先判断，再问 3–4 个核心问题

`/lts`、`/ltc`、`/ltp` 共用一套讨论规范（细节见各命令文件里的讨论步骤；`/lts` 另有内部讨论重点的局部规则）。

**每轮回复的顺序**：

1. **先给判断**：我的判断 + 依据 + 还没定的/不确定点——不要只罗列选项让用户做决策。
2. **再问 3–4 个核心问题**（硬上限 4）：真正阻塞的问题不足 3 个时不凑数；超过 4 个取最核心的
   3–4 个，其余列“待问清单”（只列标题）下一轮再问。
3. **每个问题四段式**（顺序固定，缺一不可）：

| 段 | 写什么 |
|---|---|
| 背景 | 1–3 句：从哪来、依赖哪条已定结论/被否决方案，带回指链接 |
| 问题 | 一行一个问句，一问只做一个决策 |
| 你为什么这么考虑 | 推理链、依据、不确定点、不同回答会改变什么 |
| 推荐答案 | 明确推荐一个答案 + 理由 + 选错的代价 |

**开放问题 vs 分叉决策**：

- **开放问题**（还在长、不是互斥选择）：普通对话直接问，**不给选项**；推荐答案写成“我倾向 X，因为…”。
- **分叉决策**（两边都通 + 只能选一 + 选错返工）：用 `ask_user_question`，推荐项第一，
  四段写进 `question` 字段，一次最多 4 个。

`/ltc`、`/ltp` 提问时先给 3–5 行**极简暂定大纲**（只有阶段/轮次名 + 核心目的，标注“待确认后展开”），
不展开完整计划。

**对外不播报层/相标签**：不写“当前层 / 当前相 / 相变：X → Y / 退回 X 相”。讨论重点变化时用
自然过渡（“先对一下我的判断…目前站得住的…还没定的…所以这轮…”），但要保留**已定结论 /
还没定的 / 本轮要做什么**。内部四相只作判断依据，不输出相名。

**文档元数据例外**：方案文档头部的 `> 层级：` 保留（那是文件元数据，不是对话播报）；
对话记录里不再写相名/层名标签。0.1.1 引入的“换相播报”已按此改为自然过渡（历史见
[CHANGELOG.md](../CHANGELOG.md)）。

引用前文的术语、结论、被否决方案时，第一次出现**必须**带回指链接；格式见
`skills/lignting/references/dialogue-log-format.md` 的「回指链接」一节。

## 总计划 roadmap

每个 feature 目录下有一份 `.lignting/<feature>/roadmap.md`——**人读总计划视图**，让人在一个
文件里看清“现在到哪、大轮次是什么、当前轮做什么、上一轮实际发生了什么、决策在哪”。

**定位**（硬边界）：

- **不是命令的输入**：输入链不变——`/ltc` 只读 `direction.md`，`/ltp` 只读 `phases.md`，
  `/ltw` 只读 `phase-<n>/round-<m>.md`；roadmap 不是第五层输入。
- **细节也放，但只做派生**：核心目的、要做什么、验收、改动顺序、回滚、实际结果都可写入，
  但每节标注「派生自 <源文档> · 同步于 <日期>；冲突以源文档为准」，不新造结论。
- **不写完成状态**：没有复选框、百分比、“进行中/已完成”；状态只认 whatsnext。
- 不建 `roadmap.dialogue.md`，不登记 whatsnext 文件索引。

**更新分工**（对应 `roadmap-format.md` 的 §1–§6，格式见
[roadmap-format.md](../skills/lignting/references/roadmap-format.md)）：

| 命令 | 时机 | 只动 |
|---|---|---|
| `/lts` | 方向定型、文件不存在时新建 | 头部、§1 现状与目标、§5 方向组、§6 前两行 |
| `/ltc` | `phases.md` 落盘后 | §2 大轮次（每阶段核心目的/要做什么/验收）、§1、§5 阶段组、§6 阶段行 |
| `/ltp` | `round-<m>.md` 落盘后 | §3 当前轮（核心目的/要做什么/验收/改动顺序/回滚，整块替换）、§1、§5 轮次组、§6 本轮行 |
| `/ltw` | 执行与自测完成后 | §4 执行回填（做了什么/验证结果/偏离，只追加）、§1、§6 报告行 |

从 `/ltp` 直接开始且没有 roadmap 时，先建最小框架再讨论，不阻塞。旧轮次不搬进 §3
（canonical 在各轮 round 文档）；§4/§5/§6 只追加，写错用新行更正。

**链接策略**：只用相对链接；文件级链接是硬要求，节级锚点按
[dialogue-log-format.md](../skills/lignting/references/dialogue-log-format.md) 的「回指链接」规则；
链接文字要能脱离链接看懂。例：`[direction.md 第 1 节](direction.md#1-目标与非目标)`。

## 跳层是正常用法

不是违规，是设计的一部分：

| 情况 | 走哪条 |
|---|---|
| 想法还在成形，需要探讨 | `/lts` |
| 需求已清楚，只需排期 | 直接 `/ltc` |
| 已有阶段表，只需细化某一轮 | 直接 `/ltp` |
| 已有详细计划，只需执行 | 直接 `/ltw` |
| 单点小改动 | 不用小阿卡那，走 `/ltpl` |

## 输入、无参数与子代理调度

### 输入：文字 / 图片 / 文件

- **16 个命令入口**（7 个命令文件 + 全称/别名）都支持随命令附带**图片/文件**；
  **只有附件、没有文字也算一次有效输入**，模型会从附件里取执行本命令所需的上下文。
- 图片可直接查看；文件是只读副本，消息里带文件名、大小与路径，模型按需用 `read` 读取。
- 附件能力需要 **DSH 0.2.1+**（命令的 `input.attachments` 声明）；旧版本上只能走文字输入。
- 例：`/ltck` 直接贴报错截图 + 日志文件，不写文字；`/ltc` 把 `direction.md` 作为附件发进来。

### 无参数时会怎样

| 命令 | 无参数（无文字且无附件）时 |
|---|---|
| `/lts` `/ltc` `/ltp` `/ltw` `/lt-plan` `/lt-check` | 输出**小教程**：按当前项目的真实文件/模块举例，讲用途、输入、流程、产物、当前项目实例、别名与下一层、3–5 条坑；不进入正式流程、不写文件、不反问"要不要开始" |
| `/lt-review`（`/ltrv`） | 首次（`<项目根>/.lignting/.cr-state.json` 不存在）输出小教程；之后**直接按 `middle` + 自动检测范围执行**，禁止反问审查级别、禁止要求用户重敲 `/ltrv middle` |

小教程不是静态模板：模型会先花 ≤3 步确认项目（README / package.json / 最近 git log /
目录结构，结构查询走 codegraph 且带 `projectPath`）再组织内容。读状态文件失败按首次处理。

### 子代理调度：Agent Teams 优先，回退 native

- 下发前先看当前会话工具表（不要调用不存在的工具试探），**整轮只走一套**：
  - 有 Agent Teams（`wait_agent` + `team_task_create`）→ 走 Team：`spawn_teammate` 建成员、
    `team_task_create|list|get|update` 管任务、`send_message` 回传、`wait_agent` 汇总、
    `interrupt_agent` 中断。本机成员上限 8，high 档 8 路正好占满，已有成员先复用或分批。
  - 否则回退 native：探索/审查/执行用 `subagent`，需要继承本对话已完成轮次时用
    `subagent_fork`（若目标环境挂载了 `subagent_explore`，探索优先用它；本机当前 profile
    未挂载，不是必选）。
- Agent Teams 是 DSH 官方宿主能力（随 `@deepseek-ai/dsh@0.2.1-rc.2` 自带），工具就是
  上面这些，**没有** `agent_teams_*` 工具；开启方式见
  [install.md](install.md#可选启用-agent-teams推荐)。
- 审查要求审查者 ≠ 实现者；并行写任务用 `team_task_*` 的 `blocked_by` / `write_scopes`
  约束顺序与写入范围，结果收齐再汇总。

## 跨对话：与 whatsnext 配合

小阿卡那体系与 `whatsnext` 插件（`/wn*` 命令族）分工，两边不互相复制：

| | whatsnext | 小阿卡那 |
|---|---|---|
| 解决的问题 | 我在做什么、到哪了、下一步 | 为什么这么做、方案是什么 |
| 产物位置 | `<项目>/.whatsnext/`（私有，git-ignored） | `<项目>/.lignting/`（随 git 走） |
| 谁写 | `/wn*` 命令 | `/lt*` 命令直接读写 Markdown |

四条硬规则：

1. **状态单源**：小阿卡那产出的方案文档、对话记录与 roadmap **都不含状态字段**；"这轮做完了吗"只认 whatsnext。
2. **委托而非复制**：不直接调 whatsnext 的脚本，需要时推荐用户敲 `/wn*`。
3. **粒度**：一个体系 = 一个 whatsnext 任务（层是阶段，用任务内 `plan.md` 复选框跟踪）。
4. **真源在仓库，副本要同步**：改完 skill 要同步到用户级副本，推荐做成软链
   （见 [install.md](install.md)）。

完整规则见 `skills/lignting/references/whatsnext-bridge.md`。

典型流程：

```
/wn-init                              # 首次：铺 whatsnext 地基
/wn 开始小阿卡那任务：<任务名>          # 讨论成形后：建跨会话任务
/lts <想法>                           # 宝剑层：聊方向，建 roadmap.md 框架
/ltc .lignting/<feature>/direction.md # 圣杯层：排阶段（每阶段核心目的），填 roadmap §2
/ltc <不写文字，只附 direction.md>    # 只给附件也算一次输入
/ltp .lignting/<feature>/phases.md Phase 1    # 星币层：细化当前轮，填 roadmap §3
/ltw .lignting/<feature>/phase-1/round-1.md   # 权杖层：执行，回填 roadmap §4 + 落 report
```

## `.lignting/` 文档目录约定

各层的方案文档与对话记录落在**使用方项目**的 `.lignting/<feature>/`。

**该目录随 git 走**——架构决策要能被 review；私有的只有 `.whatsnext/`。

```text
<项目>/.lignting/<feature>/
  roadmap.md                        # 人读总计划（派生视图，不是命令输入）
  direction.md                      # /lts 方案文档（方向）
  direction.dialogue.md             # /lts 对话记录
  phases.md                         # /ltc 方案文档（阶段表：每阶段核心目的 + 核心验收标准）
  phases.dialogue.md                # /ltc 对话记录（每轮追加）
  phase-<n>/
    round-<m>.md                    # /ltp 方案文档（分轮计划：核心目的 / 顺序 / 回滚）
    round-<m>.dialogue.md           # /ltp 对话记录（每轮追加）
    round-<m>.report.md             # /ltw 执行汇报（四段式）
```

**文档分三类**：

- **方案文档**——拍板后的快照，是下一层唯一输入（`direction.md` / `phases.md` / `round-<m>.md`）
- **对话记录**——追加式流水，记"为什么、否决了什么、还有什么没想清"；`/lts`、`/ltc`、`/ltp`
  每轮追加，`/ltw` 用 report 代替
- **总计划 `roadmap.md`**——跨层人读视图，细节派生自源文档、冲突以源文档为准，**不写状态**，
  也**不是任何命令的输入**

被否决的方案与理由只存在于对话记录里，方案文档不记它——那正是三个月后最值钱的部分。
