## L1 · 起点：现有 ltds 为什么不能满足讨论需求

**问**：希望和 agent 像跟资深专家喝咖啡一样讨论架构——畅想方向、评估想法的优缺点、
能否延伸；而现在的 `/ltds` 很难满足，它更偏向"实际怎么写"而非"站在架构视角审视"。

**答**：先给病根定位，不停留在症状层。

**症状 → 病根映射**：

| 症状 | 直接来源 | 病根 |
|---|---|---|
| 不聊，直接探索→提问→出文档 | 第 1/2/3 步线性不可回退 | 没有"发散"这个阶段的位置 |
| 提问题必须带选项 + 推荐项优先 | 公共约束 #4 + 第 2 步 | 把开放问题当成了分叉决策 |
| 没有观点，只有"可行性/风险" | "不得下结论"、每项必须附符号依据 | 事实纪律被误用到了构想上 |
| 结论浅 | 逐节抄 plan2/README.md | 用实现后复盘格式去装讨论 |

**关键判断**：原 `/ltds` 与 `/ltpl` 是**同一种产物的两个量级**。补了一刀——原第 3 步里
"日志与产物规范"这种章节在讨论阶段根本聊不出来，硬填就是编，恰好证明那个模板是
从"已经做完的项目"反推的。

**提出的四个设计判断**：

1. 产物不是文档，是**共识 + 方向**（文档只是记录，不是 KPI）
2. 讨论必须分相（发散/压测/收敛/定型），且每轮开头声明自己在哪一相
3. **允许构想，但必须标记置信度**——纪律从"不许说没验证的"改成"说清哪句没验证"
4. 专家价值不在"给方案"，在指出想漏的那一层（变化成本/不变量/可逆性/运维成本/过早抽象）

**当时留的两个开放问题**（即 Q1、Q2 的雏形）：讨论过程要不要落盘、收敛要不要强制收口。

## L2 · 用户提出的三层设计，以及四层化与命名

**问**：新建一个命令做讨论环节 → 结论固化成文档；再调 `/ltds` 把粗略想法细化成可实现方案、
划分每轮要做什么和验收目标；最后按每轮调命令，把一轮目标细化成最详细的修改计划，
这又需要一个新命令，模仿 ltpl 但更专业。

**答**：认可，并指出它比"改造一个命令"正确——因为它把"改 ltds"变成了"补上缺失的两层"。
链式结构的强性质：**任何一层出问题，都能定位到是哪层的产物不合格**。

同时提出用户设计里还缺的三块：

1. **ltds 的存在理由变了，必须重新定义**——原 ltds 的第 8、9 节本来就是第二层的活；
   不砍掉第 3 节的实现细节，第三层会退化成排版工
2. **需要"回冲规则"**——否则下游必然默默绕过，出现"文档写 A、代码按 B 做"
3. **需要入口闸门**——否则不改个按钮颜色也走三层，两周就被弃用

还指出第三层的"更专业"具体指四项：改动顺序、依赖闭包、回滚点、验证粒度。

**问**（用户）：这个体系要分会话使用，命名想借鉴小阿卡那，列出四个名字；
并说明文档分两部分：对话记录 + 最终方案。

**答**：确认四张牌的语义与四个阶段天然对位（风/水/土/火），不是套壳。
指出用户漏想了一层——**第四张牌（执行）是整条链的回灌通道**，没有它体系是单向盲肠。
把"两部分文档"评价为整个设计最关键的一手：解决了"为什么"的丢失、让"未定"有合法位置、
给了"重开一轮讨论"的入口。

这是第一次出现"用户方案被保留但需要修正"：三层 → 四层，不是推翻，是补上消费端。

后续用户敲定命名口径：**只用塔罗含义（Swords/Cups/Pentacles/Wands），不用扑克含义**
（Spades/Hearts/Diamonds/Clubs）；简称定为 `/lts` `/ltc` `/ltp` `/ltw`。

## L3 · whatsnext 插件能不能配合

**问**：项目里装了 whatsnext 插件（提供跨对话能力），这套命令能否配合它做更好的跨对话支持？

**答**：先去读实际实现（不猜），发现四个硬事实：

1. **真相源在仓库**：`host.js` 的 `resolveSkillDir()` 用户级优先 + 包内回退，
   而 `~/.dsh/skills/lignting` 不是软链是普通目录——两份靠手工同步，无机制保证
2. **`verify.mjs` 用正则卡路由**：`host.js` 与 `SKILL.md` 必须对齐，否则 `npm run check` 失败
3. **脚本不能直接调**：whatsnext 脚本在插件分发路径，靠其 host 注入 `${CLAUDE_PLUGIN_ROOT}`
   和真实 python 路径；本机 `python3` 指向 Windows 应用商店的假壳（执行即失败），
   真正可用的是 `python`
4. **措辞差异**：插件实际叫 `whatsnext-dsh`（口头简称 whatnext），
   位置 `D:\project\github\whatsnext-dsh`，在 profile 里以本地 link 挂载

**核心判断**：这套体系**本身已经是一套跨对话机制**，只是用文件而非会话状态承载。
跨对话能力最脆弱处在"依赖插件或会话状态"——插件改版、会话被清理链条就断；
而产物是普通文件，天然跨对话、跨插件、跨工具版本，甚至跨人。

**所以正确姿势不是"让体系依赖插件"，而是"用文档做接力，插件只负责更顺手"。**

**发现一处真冲突**：whatsnext 明确不做"手写的索引台账"，而原设计的"对话记录顶部
索引区"正好撞上它的禁止清单。解法：**状态只在一处产生，各层文档不写状态字段**；
索引只做内容分类，不做状态台账。（→ D10）

**待验证猜想 H1**：留一条轻量出口（保留 `/ltpl`），体系就不会被用成四层仪式。
验证路径：观察实际使用中小改动走 `/ltpl` 的比例。

**粒度决策**：一个体系 = 一个 whatsnext 任务，不是一个层一个任务——
层是阶段（用任务内 `plan.md` 复选框跟踪），任务是整件事（用 `index.md` 跟踪）。

## L4 · 实现与收尾

**问**：确认 A 方案（`/lts` 一开始就检查并推荐建任务），开始实现；随后要求 README 瘦身、
把原来的内部称呼改名为"小阿卡那（Minor Arcana）"。

> 注：以下保留用户当时的原话用语，不改写历史——
> 原话中的"四牌体系"即现在的小阿卡那体系。

**答**：实现并交付。过程中值得记下的两件事：

1. **"改了不生效"是真实存在的**，不是理论风险。首次跑 `npm run check` 时，
   新加的用户级副本一致性检查精确报出漂移：旧副本里 `discussion.md` 还在、
   `SKILL.md` 与仓库版不同。同步后转绿。
2. **一次操作失误**：用 PowerShell 批量替换术语时，因默认为非 UTF-8 编码读写，
   把 `.lignting/` 下两份文档的中文写成了乱码，只能重写。教训——**中文文件不要用
   PowerShell 做文本批量替换**，除非显式指定 UTF-8；用文件编辑工具更稳。

**未走的流程**：本次没有先跑 `/ltc` 排阶段再逐层 `/ltp`、`/ltw`——因为体系本身还没实现，
无法用它自己。方向文档第 8 节的阶段勾勒是**事后归纳**，不是事前规划。
这不影响本方案成立，但**下一次迭代应该真的走一遍完整流程**，
那才是对体系本身的第一个真实检验。
