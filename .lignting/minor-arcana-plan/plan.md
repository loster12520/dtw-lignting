# lignting 小阿卡那（Minor Arcana）体系改造 · 方向文档

> 层级：宝剑（/lts）
> 上游：无（本层为起点）
> 对话记录：[plan.dialogue.md](plan.dialogue.md)
> 生成日期：2026-09-21

## 1. 目标与非目标

**目标**：把 lignting 从"命令→计划"的单一通路，改造成**从想法到代码的四层递进体系**
（小阿卡那 / Minor Arcana），每层有独立产物、独立判断力，且能被下游稳定消费。

**非目标（明确不做）**：

- 不做各层命令之间的**自动串联**（`/ltw` 不自动调 `/ltp`）——每层由人决定何时进入。
- 不改 `check.md` / `review.md` / `plan.md` 三个运维命令的**内容**，只调整它们在路由表中的归类。
- 不改 `codegraph`、`karpathy-guidelines` 等其他 skill。
- 不做第四层之后的自动循环——回灌报告怎么用由人决定。
- 不为 `.whatsnext/` 手写脚手架（不复制 whatsnext 的脚本逻辑）。

## 2. 关键决策记录

### D1 · 从"改造 ltds"改为"补两层 + 重建一层"

**结论**：不改造 `/ltds`，而是新建四层体系。

**为什么**：原 `/ltds` 的隐含契约是"输入大需求 → 输出完整方案文档"，它和 `/ltpl` 是
**同一种产物的两个量级**——是"更大号的 plan"，不是另一种认知活动。所有症状（不聊、直接
探索→提问→出文档；提问必带选项；没有观点只有可行性；逐节抄固定模板）都是这个契约的派生。

**被否决的方案**：只改 `discussion.md` 的措辞和流程，保留单命令。
否决理由：病根在契约不在措辞——单命令必然同时想吃三层（聊方向、排阶段、出契约），
结果哪层都吃不透。

### D2 · 命名用小阿卡那四组牌，只说塔罗不说扑克

**结论**：`/lts`（宝剑）`/ltc`（圣杯）`/ltp`（星币）`/ltw`（权杖）。

**为什么**：四组牌的性格与四种认知模式天然对位——风（思辨切开）→ 水（愿景）→
土（务实落料）→ 火（行动推进）。命名自带记忆锚点，不增加理解成本。

**被否决的方案**：Spades/Hearts/Diamonds/Clubs（扑克叫法）。否决理由：两套名字并存会让
调用方不知道用户会喊哪个；只留塔罗，路由表里把别名写全。

**连带**：`/ltds`、`/lt-discussion` 保留为 `/lts` 的兼容别名。

### D3 · 每层两份文档：对话记录 + 方案文档

**结论**：对话记录是追加式流水（记"为什么、否决了什么、还有什么没想清"），
方案文档是拍板快照（记"定了什么"），是下一层唯一输入。

**为什么**：解决三个真问题——(1) 决策的"为什么"不会出现在方案里但三个月后最值钱；
(2) 让"未定"有了合法位置，方案文档可以只放已定项；(3) 改方案不用重写方案文档，
而是新开一段讨论再重新沉淀。

### D4 · 上游可被推翻，但偏离必须显式可见

**结论**：下游有权威推翻上游（更近实现、信息更多），但必须在产物里留"偏离项 + 理由"，
不许默默绕过。

**为什么**：多层管线最常见的死法是下游默默绕过——文档写着 A、代码按 B 做，
三个月后没人知道哪个是真的。

### D5 · 星币层只细化"即将执行的那一轮"

**结论**：`/ltp` 一次只细化一个阶段，最多前瞻一轮。

**为什么**：**细分计划有保鲜期**。把后面几轮全细化了，等真跑到那一轮计划早过期，
而执行者还会碍于"计划里写了"照做——比没有计划更糟。这条不写死，整个体系会退化成
瀑布式大计划。

### D6 · 与 whatsnext 的分工：状态归它，方案归小阿卡那

**结论**：`.whatsnext/`（私有、git-ignored）管任务状态与进展；`.lignting/`（随 git）
管方案与决策理由。**各层文档不写任何状态字段。**

**为什么**：两套系统各解决一半问题——"我在做什么/到哪了"vs"为什么这么做/方案是什么"。
两边都记状态必然漂移，且会绕过 whatsnext 的 Focus 机制。

### D7 · 委托而非复制：不调 whatsnext 的脚本

**结论**：各层只做纯 Markdown 编辑；需要建立任务、恢复任务、沉淀经验时，
**推荐用户敲 `/wn*`**，不代跑。

**为什么**（调研得出的三条硬事实）：

1. whatsnext 脚本位于**插件分发路径**，运行时的真实位置由它的 host 在每次 `/wn*` 调用时
   注入（替换正文里的 `${CLAUDE_PLUGIN_ROOT}`），外部无从得知。
2. 本机 `python3` 指向 Windows 应用商店的假壳（执行即失败），真正可用的是 `python`；
   whatsnext 的 host 会探测并注入正确解释器路径，**自己调必然踩坑**。
3. 复制它的 frontmatter 格式等于埋一处会过期的副本。

**被否决的方案**：自带一套建任务的脚手架。否决理由即上述三条。

### D8 · 保留 `/ltpl` 作为轻量出口

**结论**：`plan.md` 保留但降级，明确"不参与小阿卡那体系，只处理单点小改动"。

**为什么**：这套体系最怕被用成四层仪式。留一条明确的轻量出口，它才能保持
"用于大改造"的严肃性。

**被否决的方案**：让 `/ltp` 完全吸收 `plan.md`。否决理由：小改动也得走星币层，
体系会被用得过重。

### D9 · 局部例外机制

**结论**：命令文件可以声明对公共约束的局部例外（`lts.md` 放宽 codegraph 前置检查、
改变提问方式），例外写在命令文件里，不改公共约束。

**为什么**：架构讨论常常发生在代码之前，"先 `codegraph init -i` 再聊"会把场景卡死；
但 plan/check/review 用"带选项的提问"是对的。例外关在各自文件里，互不污染。

### D10 · 状态只在一处产生

**结论**：各层文档都不含状态字段；"这轮做完了吗"只认 whatsnext 的 `status`/`progress`
frontmatter 和任务内 `plan.md` 的 `- [x]`。方案文档里允许有「待决问题」，
但那是**内容分类**，不是状态台账。

**为什么**：whatsnext 明确"不做手写的索引台账/激活规则/修订历史"，
而原设计里"对话记录顶部索引区"正好撞上它的禁止清单。分开之后两边都不越界。

## 3. 架构方向

```
想法 ──[宝剑 /lts]──> 方向文档 ──[圣杯 /ltc]──> 阶段表 ──[星币 /ltp]──> 分轮计划 ──[权杖 /ltw]──> 代码 + 汇报
```

**楼梯式衔接**：每层只读上一层方案文档，不跨层引用。好处是每层输入面窄、可控；
允许跨层读很快就会出现"权杖层引用宝剑层某句话"这种无法追责的情况。

**跳层是正常用法**（不是违规）：需求已清楚只需排期 → 直接 `/ltc`；已有阶段表只需细化
某一轮 → 直接 `/ltp`；单点小改动 → `/ltpl`。

**每层的不可替代判断力**（写死在命令文件里，否则会退化成排版工）：

| 层 | 判据问句 | 不可替代的判断力 |
|---|---|---|
| 宝剑 | 往哪走、为什么这么走 | 分相讨论；区分开放问题与分叉决策 |
| 圣杯 | 先做哪个、什么绝不能漏 | 阶段划分；指出最核心必覆盖的能力 |
| 星币 | 具体动哪、什么顺序、怎么验证 | 改动顺序（中间态坏得最少）；依赖闭包；回滚点 |
| 权杖 | 做完没有、跟计划差在哪 | 偏离必须明说；汇报末段是回灌通道 |

## 4. 不可逆的架构契约

这几条改起来会连锁破坏，必须写死：

1. **16 个斜杠命令注册**，命令名与文件名的映射写在 `src/host.js` 的 `COMMANDS`，
   且**必须与 `SKILL.md` 路由表一致**——`scripts/verify.mjs` 用正则对撞这两处，不一致即失败。
2. **命令文件名必须是 `[a-z-]+\.md`**（`verify.mjs` 与 `host.js` 的正则形状约束）。
3. **各层文档不写状态字段**（D6/D10）——这是两系统不漂移的唯一保证。
4. **`.lignting/` 随 git 走，`.whatsnext/` 私有**——两者的 git 策略不能互换。
5. **文档头部必须有「上游」字段**——跨对话恢复与偏离比对都靠它串链条。
6. **skill 事实源在仓库，DSH 实际加载用户级副本**——改完必须同步，否则静默失效。

## 6. 风险与代价

**代价（必然付）**：

- 四层意味着**四份命令文件 + 三份格式参考**要维护，且与 `host.js`、`verify.mjs` 三处联动。
  已用 `verify.mjs` 的自动检查把漂移成本压到"跑一次 `npm run check`"。
- 每层收尾都要产出文档，比单命令多写文件。用"跳层是正常用法"来对冲——小改动不该走四层。
- 仓库版与用户级副本两份手工同步。已加自动一致性检查暴露漂移。

**风险（可能付）**：

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 被用成四层仪式 | 入场条件 + 跳层写成正常用法；保留 `/ltpl` 轻量出口 |
| R2 | 命令文件互相抄出不一致 | 抽 `references/` 公共格式，单点定义 |
| R3 | 圣杯层退化成排版工 | 把"指出最核心必覆盖能力"写成硬产出，验收按此检验 |
| R4 | 细分计划过期 | 星币层只细化即将执行的那一轮 |
| R5 | 与 whatsnext 争状态真相 | 硬规则：各层文档不写状态字段 |
| R6 | `/ltp` 与 `/ltpl` 混淆 | 两处文档都加了显式提醒；简称设计上无法完全避免，靠提醒 |

## 7. 验证信号

怎么知道这个方向是对的：

- **能用一句话说清每层在干什么**，且四句话互不重叠——重叠说明层次没切干净。
- **新开一个对话，只跑 `/wn` 恢复，能说出"下一步该敲哪条命令"**——跨对话能力成立的硬信号。
- **小改动走 `/ltpl` 而不走四层**——说明轻量出口有效，体系没有被用成仪式。
- **`npm run check` 全绿**，包括用户级副本一致性。
- **`/ltw` 的汇报里「与计划的偏离」一节非空且诚实**——空着或含糊说明执行层没在核对现实。
